Two function names turn up when you search for UUIDv7 in Postgres, and only one of them ships with the server. This page is the reference I wanted when I wrote my [UUIDv7 benchmark post](/blog/uuidv7-postgres-comparison/): one question per heading, the answer in the first sentence, sources at the end.

## Which function do I call, uuidv7() or uuid_generate_v7()?

Call `uuidv7()`. It is built in since PostgreSQL 18, together with `uuidv4()` as an alias for `gen_random_uuid()`, and it is the same in PostgreSQL 19. `uuid_generate_v7()` is not a core function in any PostgreSQL version. The signature is:

```text
uuidv7 ( [ shift interval ] ) → uuid
```

The optional argument is an `interval`, not a timestamp. It moves the timestamp that goes into the UUID by that amount, so `uuidv7(interval '-1 hour')` produces an ID dated one hour ago. An infinite interval is rejected, and a shift outside the 48-bit timestamp range raises an error.

`uuid_generate_v7()` comes from outside core. The `pg_uuidv7` extension defines a function with that name, along with `uuid_v7_to_timestamptz()` and `uuid_timestamptz_to_v7()`, for Postgres 13 through 18. A PL/pgSQL gist by kjmph uses the same name, and so does the PL/pgSQL function in my earlier post. When the name appears in a schema, check which one is installed.

The name looks like it belongs to `uuid-ossp` because of `uuid_generate_v4()`. It does not. `uuid-ossp` generates versions 1, 3, 4 and 5 only.

## Which PostgreSQL versions have UUIDv7?

PostgreSQL 18 and 19 have it built in. Older versions do not.

| Version | Generate a UUIDv7 | Read its timestamp |
| --- | --- | --- |
| 19 | `uuidv7()` | `uuid_extract_timestamp()` |
| 18 | `uuidv7()` | `uuid_extract_timestamp()` |
| 17 | not built in | not built in; `uuid_extract_timestamp()` reads version 1 only |
| 16 and older | not built in | not built in |

On 17 and older there are three ways to get a version 7 value:

| Option | What you run | Trade-off |
| --- | --- | --- |
| Extension | `CREATE EXTENSION pg_uuidv7;` then `uuid_generate_v7()` | Needs the extension files on the server, which a managed provider must allow |
| SQL or PL/pgSQL function | A `CREATE FUNCTION` you keep in a migration | No install step, but you own the code |
| Application | Any UUIDv7 library, inserted as a normal `uuid` | IDs from several clients are ordered only by their clocks |

All three store into the same `uuid` column, so moving to the native function later is only a change of default. Three SQL implementations and their timings are in the [benchmark post](/blog/uuidv7-postgres-comparison/).

## How long is a UUIDv7, and how many bytes does it take?

A UUIDv7 is 128 bits, the same as every other UUID version. Its text form is 32 hexadecimal digits in groups of 8, 4, 4, 4 and 12, which comes to 36 characters with the four hyphens.

| Form | Size | Why |
| --- | --- | --- |
| `uuid` column | 16 bytes | `typlen` of 16 in the `pg_type` catalog |
| `text` or `varchar` | 37 bytes | 36 characters plus a 1-byte length header |
| `bigint`, for comparison | 8 bytes | fixed width |

<KeyBytes />

Storing the ID as text costs more than twice the space in the table and again in every index that contains the column, and RFC 9562 says the same thing in general terms: where feasible, store UUIDs as the underlying 128-bit value.

I measured it with 10 million rows. The primary key index was 301 MB for a `uuid` column and 563 MB for the same UUIDv7 values as `text`. The table grew from 498 MB to 730 MB.

## What is inside a UUIDv7?

RFC 9562 defines five fields, in this order:

| Field | Bits | Content |
| --- | --- | --- |
| `unix_ts_ms` | 48 | Unix time in milliseconds, big-endian |
| `ver` | 4 | `0111`, the version |
| `rand_a` | 12 | Random, or extra clock precision |
| `var` | 2 | `10`, the variant |
| `rand_b` | 62 | Random, or a counter |

The RFC lets an implementation choose how to use `rand_a`. PostgreSQL uses the option the RFC calls Method 3: the 12 bits hold the fraction of the current millisecond, in steps of 1/4096. So a native value is the millisecond timestamp, then the sub-millisecond fraction, then random bits. That leaves the 62 bits of `rand_b` as the random part of a native value, against 74 random bits for implementations that fill `rand_a` randomly, which is what `pg_uuidv7` does.

## How do I read the timestamp back out?

Use `uuid_extract_timestamp()`, which returns a `timestamp with time zone`:

```sql
SELECT uuid_extract_timestamp('019535d9-3df7-79fb-b466-fa907fa17f9e'::uuid);
-- 2025-02-23 21:46:24.503-05

SELECT uuid_extract_version('019535d9-3df7-79fb-b466-fa907fa17f9e'::uuid);
-- 7
```

The version matters here. Both functions arrived in PostgreSQL 17, but on 17 `uuid_extract_timestamp()` returns null for anything other than version 1. Version 7 support came with 18. So a UUIDv7 made by an extension on 17 cannot be decoded with the built-in function on 17; `pg_uuidv7` has `uuid_v7_to_timestamptz()` for that.

The result has millisecond precision, and it is not necessarily the exact generation time.

## Is uuidv7() monotonic?

Within one backend, yes; across backends, no. The commit that added the function says monotonicity "is ensured within the same backend", including when the system clock goes backward or when values are generated at very high frequency. The source does this by forcing each timestamp to be at least one step later than the previous one that backend handed out.

A backend is one server process, which in practice means one connection. Two connections each keep their own last timestamp, so their values interleave by clock reading, and two servers have no relationship at all beyond their clocks.

It also says nothing about commit order: a transaction that takes its ID first can commit last, exactly as with a sequence.

I measured both cases on 19.0. One statement generated 1 million values in one backend. None was smaller than or equal to the value before it, and they spread over 515 distinct milliseconds, about 1,900 values per millisecond, all kept in order by the 12-bit fraction and the step forward. Then pgbench made 200,000 inserts from 8 connections into a table with a `bigserial` column next to the `uuidv7()` default. Ordered by the sequence, 1,286 rows, 0.64%, had a smaller UUID than the row before them. Grouped by backend, there were none.

One small surprise: `min()` and `max()` have no `uuid` version on 19.0, and `SELECT max(id)` fails with `function max(uuid) does not exist`. `ORDER BY id DESC LIMIT 1` reads the same value from the index.

So `ORDER BY id` on a UUIDv7 key is a good approximation of creation order and a correct order within one connection. It is not a replacement for a sequence where gaps and reordering matter, such as an outbox table that consumers read with `WHERE id > last_seen`. A row that commits late with a slightly older ID falls behind a cursor that already moved past it. That problem exists with a sequence too, and the fix is the same: read only rows older than a safety margin, or track position some other way.

## What does it cost to index, compared with UUIDv4 and bigint?

A UUIDv7 key behaves like a `bigint` from a sequence in where it lands, and like a UUIDv4 in how wide it is.

New version 7 values are larger than older ones, so every insert goes to the right-hand edge of the B-tree. The same few leaf pages take all the writes. PostgreSQL also treats that edge specially: leaf pages are filled to the `fillfactor`, 90 by default, when the index grows at the right with new largest keys.

A version 4 value is random, so each insert picks a leaf page anywhere in the index. Once the index is larger than memory, that page often has to be read from disk first, and pages that fill up are split wherever they happen to be. There is a WAL effect too. With `full_page_writes` on, the first change to a page after a checkpoint writes the whole page to WAL, and random inserts touch far more distinct pages between checkpoints than inserts at one edge do.

Against `bigint` the difference is size alone: 16 bytes per key against 8, in the primary key index and in every foreign key and index that references it.

## Does REINDEX fix a bloated UUIDv4 index?

For a while. A rebuild packs the leaf pages to the `fillfactor`, so the version 4 index loses its extra size, but the next random inserts split those full pages again.

For this and the next two sections I built a second pair of 10 million row tables in one `INSERT ... SELECT` each, with a `created_at timestamptz` column filled by `clock_timestamp()` beside the key. The version 4 primary key came out at 380 MB with leaf pages 71% full.

After `REINDEX` it was 301 MB with pages 90% full, the same as the version 7 index. Then I inserted 1 million more rows into each table.

Ten percent more rows took back almost all of what the rebuild saved, because nearly every page was full and every random insert into a full page splits it. The version 7 index grew by 30 MB, which is the space the new keys need. A scheduled `REINDEX CONCURRENTLY` on a version 4 key holds its gain only until the table grows by another few percent, and it costs a full index build each time.

## How many pages does it take to read recent rows?

Far fewer with version 7, because the newest keys sit together. Most applications read recent rows more often than old ones: the latest orders, the active sessions, the events of the last hour. I took the 10,000 newest IDs from each table, restarted the server to empty `shared_buffers`, and looked them up by primary key with `EXPLAIN (ANALYZE, BUFFERS)`. Both plans were index-only scans with 10,000 loops.

<NumberBand value="43" note="against 9,220 for uuidv4()">
  index pages read from outside `shared_buffers` to look up the 10,000 newest `uuidv7()` keys, in 7 ms against 51 to 59 ms.
</NumberBand>

The version 7 lookups touched 43 pages that were not already in memory, because 10,000 adjacent keys fill about 40 leaf pages. The version 4 lookups read 9,220 pages, 72 MB, since each recent key sits on a different leaf. The operating system cache still held the whole index, so these were memory copies and not disk reads. With an index that does not fit in RAM, each of those 9,220 pages can be a disk read, and the same pages compete with everything else for `shared_buffers`. Insert speed is the usual argument for version 7. For a read-heavy service this working-set effect may matter more.

## Can the primary key replace a created_at index?

For range queries by time, yes, with care. The leading 48 bits of a version 7 value are the creation time, so all IDs created at or after a given millisecond are greater than or equal to the smallest UUID for that millisecond. PostgreSQL has no function that builds that bound, but it is one line of SQL:

```sql
CREATE FUNCTION uuidv7_floor(ts timestamptz) RETURNS uuid
LANGUAGE sql IMMUTABLE PARALLEL SAFE AS $$
  SELECT (lpad(to_hex(floor(extract(epoch FROM ts) * 1000)::bigint), 12, '0')
          || '70008000000000000000')::uuid
$$;

SELECT sum(v) FROM events WHERE id >= uuidv7_floor(now() - interval '1 hour');
```

The tail sets the version to 7, the variant bits to `10` and everything else to zero, which is the smallest valid version 7 value for that millisecond. Because the function is immutable and its argument here was a constant, the planner folded it, and the plan showed a plain `Index Cond: (id >= '01a1ff4c-f20f-7000-8000-000000000000'::uuid)` on the primary key.

I picked the timestamp of the 100,001st newest row and queried from there three ways:

The 98 extra rows are the rest of that millisecond. The UUID carries the time at millisecond precision, so the floor includes every row from the start of the millisecond, while `created_at` has microseconds. For a dashboard or a retention job that difference does not matter. For an exact boundary it does.

The BRIN row is the interesting one. A BRIN index with the default `uuid_minmax_ops` stores the smallest and largest value per range of 128 heap pages. Because the rows were inserted in key order, those ranges do not overlap, and a 48 kB index answered the range query as fast as the 210 MB B-tree. It recheck-filtered 12,157 rows from lossy pages to get there.

Three things break the assumption that ID order is time order. IDs made with `uuidv7(interval '-1 hour')` or similar shifts are dated by the shift. IDs made in the application carry the application's clock. And a column migrated from `gen_random_uuid()` still holds version 4 values, which are spread over the whole key range, so a range on `id` returns an arbitrary sample of old rows. If any of these apply, keep `created_at` and its index. The BRIN index also degrades when rows are updated or inserted out of key order, because each page range then covers a wider span of values.

## Does a UUIDv7 leak the creation time?

Yes. The first 48 bits are the creation time in milliseconds, and `uuid_extract_timestamp()` reads it in one call. RFC 9562 calls this "a very small attack surface" and notes that the timestamp signals the order of creation.

That matters when the ID leaves your system and the time is something you would not print next to it: a user ID in a public URL shows when the account was made. It also matters when the ID doubles as a secret, as in a password-reset link. For any security use the RFC's advice is to use UUIDv4.

## How do I switch a column from gen_random_uuid() to uuidv7()?

Change the default. Both functions return `uuid`, so the column type stays as it is.

```sql
ALTER TABLE orders
  ALTER COLUMN id SET DEFAULT uuidv7();
```

The new default applies only to later `INSERT` and `UPDATE` commands, and existing rows do not change.

The column then holds both versions. The old version 4 values are spread across the whole key range, and the new ones sit together in one narrow, slowly advancing part of it, because their leading bits are the current time. `uuid_extract_version(id)` tells the two apart, and `uuid_extract_timestamp(id)` returns null for the version 4 rows, so keep `created_at` if you rely on it.

On PostgreSQL 17 or older with `pg_uuidv7`, the same statement works with `uuid_generate_v7()` as the default.

I made the switch on the 11 million row version 4 table from the REINDEX test. The next million inserts took 1.5 s, the same as a million inserts into the pure version 7 table, against 6.7 s for a million more version 4 values into the same index. The insert cost improves on the day of the switch, with no rewrite of old rows.

The space does not improve as much. Those million keys grew the index by 54 MB, where the pure version 7 index grew by 30 MB for the same count. A version 7 value made in late 2026 starts with `01a`, so the new keys do not go to the right-hand edge of a mixed index. They go to one spot less than 1% of the way into its key range, among old version 4 keys with the same leading digits, and the splits there do not get the right-edge fill. The inserts stay local, which is what makes them fast, but each page they split ends up less full. The bloat the old values caused stays until a `REINDEX`, and after that the new values add less than random keys would.

## When to use which key

`bigint` from an identity column is still the smallest and fastest key when IDs are created only by the database and never leave the system, or leave it where a counter is acceptable. It is half the size in every index and foreign key, and in my runs it loaded 10 million rows in two thirds of the time.

`uuidv7()` is the default I use for new tables whose IDs are exposed or generated in more than one place: public APIs, merged data from several databases, IDs that the client creates before the insert. It costs the extra 8 bytes per key and almost nothing else, and it brings the read locality from the section above.

`uuidv4()` is the right choice when the ID must not reveal anything, including order and creation time: tokens, invitation codes, anything used as a secret. For those tables the insert and index costs above are the price, and on a small table nobody notices it.
