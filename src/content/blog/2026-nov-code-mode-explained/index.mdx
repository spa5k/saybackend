Agents and the models, are very good in writing code, even better than us lots of times, but the process of tool call is still sequential looping (there are things like parallel tool call), but it's same thing, the agent needs to call each tool as many times as needed, and each sending their output.

In this post, we will try to explain Code Mode, how it works, and how it replaces most of the above loop with one single step, the model writes a simple program against an API, it runs in a sandbox, and only the required and needed return values goes back to the model. We will try to explain where is the sandbox run, where codemode is useful, where it's not, and the costs.

This post is focused on Cloudflare's initial exploration of Code Mode, their [first post](https://blog.cloudflare.com/code-mode/) and the [`@cloudflare/codemode`](https://github.com/cloudflare/agents/tree/main/packages/codemode) package, so most of the examples and numbers here come from it. Anthropic's version gets a short section, and the other harnesses get their own posts later in this series.


{/* An agent with tools runs a loop. The model picks a tool, the harness runs it, the result goes back into the context, and the model picks the next tool. Code mode replaces most of that loop with one step: the model writes a program against a typed API, a sandbox runs it, and only the program's return value goes back to the model.

 This post explains the mechanism and the two designs it came from. It also covers what the sandbox has to block and where code mode is the worse choice. I measured the costs on a real tool list and ran the real Cloudflare executor locally. */} 

## What is the tool-call loop and what it costs

The classic tool loop has three parts:

{/* - **Definitions.** Every tool's name, description and JSON Schema is in the context on every turn, used or not.
- **Results.** Every tool result passes through the model, even when the model only needs one field of it.
- **Round trips.** Each call is one model turn. Ten dependent calls are ten turns, and each turn reads the whole context again. */}

- **Definitions** - The tool's JSON schema, name, description, is in context in every turn (it's not always the case depending on your harness, there are things like [deferred tool loading](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) btw)
- **Results** - Every tool call sends back a result, even if it's a failure, back to the model, even when model might just be needing a single field.
- **Round Trips** - If one call is dependent on the other, it amounts to 10 separate calls.

To prepare a realistic dataset, I took the tool list from [GitHub's official MCP server](https://github.com/github/github-mcp-server), [v2.2.0](https://github.com/github/github-mcp-server/releases/tag/v2.2.0), by calling the `tools/list`. The default toolset has total of 46 tools, and we will be using [o200k_base](https://github.com/openai/tiktoken) tokenizer for the counting of tokens.

Serializing the tool definitions with name, description, and input schema for these 46 is around 11k tokens. average of 242 tokens per tool, `issue_write`, the one with highest token is 803 tokens.
And for the data, I decided to run it on recent issues of the [cloudflare/agents](https://github.com/cloudflare/agents/issues) from the public REST API. Each issue came to between 384 and 2,572 tokens, 889 on average.

{/* For a realistic fixture I took the tool list of GitHub's official MCP server, v2.2.0, by calling `tools/list` on its Docker image. The default toolsets have 46 tools. All token counts in this post use the o200k_base tokenizer; Claude's tokenizer gives different absolute counts, so read the ratios.

Serialized as JSON with name, description and input schema, the 46 definitions are 11,132 tokens, 242 per tool. The largest, `issue_write`, is 803 tokens.

For results, I fetched the 20 most recent issues of `cloudflare/agents` from the public REST API. I shaped each one the way the server's `issue_read` tool does, with a port of its `convertToMinimalIssue` function. Each issue came to between 384 and 2,572 tokens, 889 on average. */}

## What will codemode change?

> We will be using [cloudflare/codemode](https://github.com/cloudflare/agents/tree/main/packages/codemode) as reference for this blog, in future posts, we will explore more ways of codemode.

Now, the model will only get one tool, which is `code`, the description contains the tools as a TypeScript API. Here is how codemode renders `issue_read`.


{/* The model gets one tool, `code`, whose description contains the tools as a TypeScript API. Here is `issue_read` as `@cloudflare/codemode` 0.5.6 renders it, shortened: */}

```ts
type IssueReadInput = {
    /** The number of the issue */
    issue_number: number;
    /** The read operation to perform on a single issue. ... */
    method: "get" | "get_comments" | "get_sub_issues" | "get_parent" | "get_labels";
    owner: string;
    repo: string;
}
type IssueReadOutput = unknown

declare const codemode: {
	issue_read: (input: IssueReadInput) => Promise<IssueReadOutput>;
	// ... 45 more
}
```

{/* The model answers with JavaScript, not with a tool call. This is the program for "list the open issues with no assignee among these 20":
 */}
Because, now the model only has one tool, `code`, it answers with JavaScript, not with a tool call. Below is the program to "list the open issues with no assignee among these 20":

```js
async () => {
  const numbers = [2924, 2920, 2917, 2916, 2915, 2911, 2910, 2909, 2906, 2905,
                   2904, 2902, 2901, 2900, 2897, 2893, 2892, 2891, 2888, 2883];
  const unassigned = [];
  for (const issue_number of numbers) {
    const issue = await codemode.issue_read({
      method: "get", owner: "cloudflare", repo: "agents", issue_number
    });
    if (issue.state === "open" && issue.assignees.length === 0) {
      unassigned.push({ number: issue.number, title: issue.title, comments: issue.comments ?? 0 });
    }
  }
  return unassigned;
}
```

Just from the code above, you can see how big of a saving of tokens it will be for the model while making sure required data still reaches the model.

## Where does the name come from

Cloudflare named it as such. [Kenton Varda](https://github.com/kentonv) and [Sunil Pai](https://sunilpai.dev) published ["Code Mode: the better way to use MCP"](https://blog.cloudflare.com/code-mode/) on September 26, 2025 (Already more than a year old, which is like a decade older in this AI era). Their argument: “LLMs have seen a lot of code. They have not seen a lot of "tool calls".” (Which was true that time, but not today imo)

In the first design, it was pretty much all client side, the agent harness when it connects to an MCP server, it analyzes it and converts its tool schemas into a TypeScript API with comments, and gives the model only one tool to run the code. The code then runs on the new [V8 Isolate](https://developers.cloudflare.com/workers/reference/how-workers-works/), in Cloudflare's [Worker Loader API](https://developers.cloudflare.com/dynamic-workers/).

{/* The first design is client-side. The agent connects to an MCP server, converts its tool schemas into a TypeScript API with doc comments, and gives the model one tool that runs code. The code runs in a new V8 isolate from the Worker Loader API. MCP servers reach the isolate as bindings, so the isolate needs no network, and the host adds credentials, so the generated code never sees a key. */}


{/* The full API sits in the context, and the TypeScript rendering is larger than the JSON it came from. */}
And as you can expect, the full API sits in the context, and the TypeScript result context is larger than the JSON it came from.

### One run through `@cloudflare/codemode`

{/* Let's follow one run from start to end. `createCodeTool` gives you a normal AI SDK tool, and its only input is `{ code: string }`. */}
Now, let's try to follow one run from start to end using the `createCodeTool`, it gives you a normal AI SDK tool, and the only input is `{ code: string}`.

When the model calls this tool, the code does not run instantly, it first goes through the normalizer first (`normalizeCode`), it mainly helps to make sure the code is consistent, since models love to wrap code in markdown fence, and that is stripped. It accepts pretty much anything, an arrow function, export default, a named function, etc. Statements are wrapped in an async arrow function, and if the last one is an expression, it becomes the value to be returned. So even `codemode.get_me({})` alone works.
{/* When the model calls it, the code does not run right away, it goes through `normalizeCode` first. Models love to wrap code in a Markdown fence, so that gets stripped, and then it accepts pretty much any shape: an arrow function, `export default`, a single named function, or just a list of statements. Loose statements get wrapped in an async arrow function, and if the last one is an expression, it becomes the return value. So even `codemode.get_me({})` alone works, and a model that ignores the "write an async arrow function" instruction still gets its program run. */}

{/* Then the executor builds a fresh module for this one run, and inside it: */}
Then it builds a fresh module for this one run, and it handles these cases as well - 

- `console.log`, and `warn/error` does not print anywhere, they are pushed to an array.
- Every tool call goes back to the host, and the host validates the input with the AI SDK's schema check before the tool's `execute` runs.
- If a tool throws, the program gets a normal `Error` with the same message, so it can catch it like in any other code.
- If the program finishes while a tool call is still pending, that call gets answered with "The code execution finished before this tool call settled. Await every tool call before returning." (a forgotten `await`, basically)
- The whole program is raced against a timeout.

{/* A failed run does not lose its logs, which is nice. The model gets `Code execution failed: <message>`, with the console lines below it under "Console output:". So if the program logs each step, the model still sees the partial results. Keep this in mind, it matters for the debugging case further down. */}
A failed run keeps its logs, which is quite nice, the model gets `Code execution failed: <message>`, with the console lines below it as `Console output:`, so if the program logs at each step, it can still see the partial results, which is useful for debugging case.
{/* The sandbox itself is just an interface, and the package ships two of them: */}
The Sandbox is just an interface, and it by default, ships two of them.

| Executor | Runs in | Isolation | Default timeout |
| --- | --- | --- | --- |
| `DynamicWorkerExecutor` | a Worker, through the Worker Loader | no network (`globalOutbound: null`) | 60 s |
| `IframeSandboxExecutor` | the browser, in a hidden iframe | `sandbox="allow-scripts"` and a strict Content Security Policy, tool calls over `postMessage` | 30 s |

Anything that implements `execute(code, providers)` can take their place, so you can bring your own sandbox as well.

{/* Then there's the second design, where the work moves to the server. On February 20, 2026, [Matt Carey described](https://blog.cloudflare.com/code-mode-mcp/) Cloudflare's(add link) MCP server for its own API. That API has over 2,500 endpoints, and the server covers all of them with just two tools: */}
Then there's the second design, since its obvious there's a problem of having all in context, so we add a new tool to search the API spec beforehand, [Matt Carey described](https://blog.cloudflare.com/code-mode-mcp/) [Cloudflare's](https://github.com/cloudflare/mcp) MCP server for its own API in this format.

- **`search()`** - runs model-written JavaScript against the OpenAPI spec, so the model filters the spec instead of reading the whole thing.
- **`execute()`** - runs model-written JavaScript that calls the API through `cloudflare.request()`.

## Anthropic's version
Anthropic wrote about a similar idea a few weeks later as well. On Nov 4, 2025, Adam Jones and Conor Kelly published the ["code execution with MCP"](https://www.anthropic.com/engineering/code-execution-with-mcp). In Anthropic's case, each MCP tool becomes its own TypeScript file, like `./servers/google-drive/getDocument.ts`. The agent can then normally list the directory and read what's needed, so context is not filled.

{/* Anthropic wrote about the same idea a few weeks later(add link to it). On November 4, 2025, Adam Jones and Conor Kelly published ["Code execution with MCP"](https://www.anthropic.com/engineering/code-execution-with-mcp). Here, each MCP tool becomes its own TypeScript file, like `./servers/google-drive/getDocument.ts`. The agent lists the directory and reads only the files it needs, so the definitions load on demand instead of all of them sitting in the context. */}

The Claude API also has a managed version of this, called [programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling). It's built on the code execution tool (version `code_execution_20260120` or later), and the language here is Python, not JavaScript. A tool opts in with `allowed_callers`:

```json
{
  "tools": [
    { "type": "code_execution_20260521", "name": "code_execution" },
    {
      "name": "issue_read",
      "description": "Get information about a specific issue in a GitHub repository.",
      "input_schema": {
        "type": "object",
        "properties": { "issue_number": { "type": "number" } },
        "required": ["issue_number"]
      },
      "allowed_callers": ["code_execution_20260521"]
    }
  ]
}
```

{/* The interesting part is that Anthropic does not run your tool. When the Python code calls it, the code pauses, and the API returns a `tool_use` block whose `caller` points to the code execution run. Your application runs the tool, sends back a `tool_result`, and the code continues from where it paused. These results don't enter Claude's context and don't count toward token usage, only the final output of the code does. */}

Check the diagram below, it shows where the code pauses and who runs what.

<PtcPause />

There are some limits you should know before you design around it. Tools from the MCP connector can't be called this way, and neither can tools with `strict: true`. Each Python cell gets 90 seconds of wall-clock time, and a pending tool call times out after about 4 minutes. The container has no internet access, 5 GiB of memory and one CPU.

Anthropic's own numbers show where the feature helps and where it doesn't. On a 75-tool project-management benchmark, it cut billed input tokens by about 38 percent, with no change in accuracy. On τ²-bench, where each turn makes one or two sequential calls, the scores stayed the same and it cost about 8 percent more. So it's not a free win, it depends on how many calls your task chains together.

## The arithmetic for N calls

{/* Now let's do the math. These numbers are arithmetic on the sizes I measured above, not real model runs. */}
Now let's do some math and assumptions.

{/* The task reads N issues. In the direct loop, that's one issue per turn, and each turn reads the definitions, the prompt, and every earlier call and result again. Code mode takes two turns, one to write the program and one to read its return value. Search and execute adds one more turn, to read the `issue_read` schema. */}
The imaginary task here reads N issues. In a loop, that's one issue each turn, and each turn reads the definitions, the prompt, and every earlier call and its result again (while its a prefill phase, and is faster and cheaper but it's there). In Codemode, it takes two turns, one turn to write the program, and one to read the result. Search and execute can add one more turn to read the schema, but due to deferred tool loading, agents do that even in non codemode way as well.

## How are permissions handled

The sandbox has a simple job. It gives the program its tool functions, a way to return a value, and a time limit. Everything else, it denies: the network, the filesystem, the environment and the host process. The tools are the only door out, and the credentials stay on the host side of that door, so the generated code never sees a key.

`@cloudflare/codemode` builds a module for each run. Each namespace, like `codemode`, is a `Proxy`, and its methods send the call to a `ToolDispatcher` on the host over Workers RPC. The Worker is loaded with `globalOutbound: null`, so it has no network at all.

I wanted to see it for myself, so I ran some probe programs through the executor. Each line is the program, then what came back:

- `await fetch("https://example.com")`: `This worker is not permitted to access the internet via global functions like fetch(). It must use capabilities (such as bindings in 'env') to talk to the outside world.`
- `connect("example.com:80")` from `cloudflare:sockets`: the same error.
- `await import("node:fs")`: `No such module "node:fs".`
- `Object.keys(process.env)`: `[]`.
- `throw new Error("rate limit reached, stopping")`: the message as the error string, `rate limit reached, stopping`.
- `await new Promise(() => {})` with a 3-second timeout: `Execution timed out` after 3,004 ms.
- `while (true) {}` with a 3-second timeout: no response after 120 seconds.

Check the diagram below to see where the boundary sits.

<SandboxBoundary />

The infinite loop is the interesting one. The executor's timeout is a `setTimeout` raced against the program, and a synchronous loop never gives the timer a chance to fire. Locally, `workerd` stayed at 91% CPU, and even a new `1 + 1` request got no answer within 20 seconds. On Cloudflare's network, the platform's CPU limits stop a Worker like this, and Dynamic Workers accept lower custom limits too. But the lesson holds for any executor you build, the time limit must come from the runtime, not from code that runs inside the sandbox.
