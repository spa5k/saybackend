Coding agents write most of the code in our monorepo at work, and for a long time we gave them our rules the usual way: skill files, and a guide they read before they start. It worked only in part. An agent could quote a rule from that text and break it in the same task, and the fix then fell to a reviewer.

So I changed the approach. Between August and November 2026 I moved every rule that a program can check out of the text and into the linter. (The skills themselves are older, from May.) It ended up as three steps:

1. **Turn the instruction into a lint rule.** We now have 24 rules of our own, next to 18 from a public ruleset.
2. **Record the old violations, and let no count go up.** The code already broke these rules 26,332 times. A baseline lets those stay, and fails the build for one more.
3. **Close the ways around it.** A pull request can't raise its own allowed count, and a new "disable this rule" comment is itself a violation.

The number I watch is the total. It merged at 26,332 on 17 November. As of 23 November 2026 it is 25,787: 545 fewer, or 2.1%, with no cleanup project.

The August step has [its own post](/blog/lint-ai-generated-code/) with the first rules in detail. The public ruleset is [`dmmulroy/anti-slop`](https://github.com/dmmulroy/anti-slop). Rules without a prefix in this post are first-party rules we wrote for our repository.

## An instruction is a suggestion

A skill is a text file with instructions for a coding agent. We had one for React effects with 312 lines and one for React architecture with 224. The text was sound. The agent read them, then read the code around its task, and the code won. When a file already has ten effects that copy one value into another, the eleventh one looks normal.

A lint rule doesn't care what the agent read. It's a small program that reads the code after it's written. The same line gets the same error from every author: an agent, another agent, or me. If you've ever replaced a "please validate input" comment in a handler with an actual schema check, it's the same move.

There was also a specific motivation. During this work I wrote in one thread: "I don't like how models always add a comment to avoid fixing things. It's better to fix than to leave it." And later: "We should not allow the agent to add disable directives at all." Most of what follows comes from those two positions.

## Step 1: turn the instruction into a rule

For each instruction I ask one question. Can a program see this in the code, without knowing what the feature is for? If yes, it becomes a rule. If no, it stays in the skill.

| The instruction, in plain words | The rule | What the rule reports |
| --- | --- | --- |
| Do not add an effect to keep two values in sync | `no-use-effect` | An effect, counted per file |
| Do not build a debounce from a timer in an effect | `no-effect-debounce` | A timer in an effect, when the timer callback sets state |
| Read the pending state from the mutation | `no-manual-pending-state` | A boolean state that copies the status of a mutation |
| Keep each query key in one place | `no-inline-query-key` | A query key written as an array at the call site |
| Call the server through the typed client | `no-client-fetch` | A raw `fetch` in a client module |
| A feature does not import another feature | `no-cross-feature-import` | An import from one feature folder into another |
| Do not hide an error | `no-swallowed-error` | A `catch` that never reads the error that it caught |
| Do not wait for a fixed time | `no-inline-sleep` | A promise that only resolves from a timer |
| Parse external JSON with a schema | `no-json-cast` | A type assertion on the result of `JSON.parse` or `response.json()` |
| Do not classify an error by its text | `no-error-message-match` | A branch on `includes`, `match` or a regex test of an error message |
| Production code does not know about tests | `no-test-awareness` | A check for a test run, or an export that only tests use |

The November rules came from a review of the whole code base with several models. They kept finding the same five shapes: a comment that explains a workaround in place of a fix, a disable directive, an `as` cast on parsed JSON, a `catch` that drops its error, and a feature that imports another feature. Each one is a rule now.

Some instructions stayed in the skill, because they need intent. Which part of the app owns a piece of state, when a form must reset, whether a search waits for the user to stop typing: those are product decisions. A linter can't see them.

With the rules in place, the text could shrink. That happened in October, before the baseline: the two React skills, 536 lines together, became one skill with 54. It's 58 lines today. It says what to decide and points at the lint rules for everything else. Its core is a table of owners for state:

| State | Owner |
| --- | --- |
| Computed from props, a query, or the URL | Derive it during render |
| Remote data and the status of a mutation | The query library |
| Search, filters, tabs, or a selection that a user can share | The URL |
| Form input and validation | The form library |
| A local dialog or interaction | The leaf component |
| Client state that distant components share | A small store inside the feature |

The rest is a list of behaviours to compare after a change: loading, error and empty states, back navigation. No rule can judge those.

The code review skill got the matching line. It tells the reviewer that lint already rejects the mechanical cases, names them, and says: "Do not repeat them as findings."

### What a rule looks like

A rule is a function that visits the syntax tree of a file and reports the shapes it doesn't accept. This one is shortened for the post. It finds `new Promise((resolve) => setTimeout(resolve, 500))`.

```ts
import { defineRule } from "@oxlint/plugins";

export const noInlineSleep = defineRule({
  meta: {
    type: "problem",
    messages: {
      inlineSleep:
        "A fixed sleep guesses how long something takes. Wait on the real condition instead.",
    },
  },
  createOnce(context) {
    return {
      NewExpression(node) {
        if (node.callee.type !== "Identifier" || node.callee.name !== "Promise") return;
        const [executor] = node.arguments;
        if (executor?.type !== "ArrowFunctionExpression") return;
        const [resolve] = executor.params;
        const body = executor.body;
        if (
          resolve?.type === "Identifier" &&
          body.type === "CallExpression" &&
          body.callee.type === "Identifier" &&
          body.callee.name === "setTimeout" &&
          body.arguments[0]?.type === "Identifier" &&
          body.arguments[0].name === resolve.name
        ) {
          context.report({ node, messageId: "inlineSleep" });
        }
      },
    };
  },
});
```

Three things I learned from writing 24 of these:

- **The message is written for the agent.** It says what to do instead, because the agent reads the error and tries again. The message of `no-type-assertion` is a fair sample: "This assertion makes the checker trust a type it cannot prove. Fix the declaration that produced the wrong type, narrow with a type guard or a schema, or use `satisfies` to check a literal." And it works: when the ratchet caught our own verification scripts, the agent added a `closeCdpBrowser()` helper instead of `.catch(() => {})`, and rethrew anything that wasn't a `SyntaxError` from `JSON.parse`. Code changes, not directives.
- **A custom rule sees the shape of the code and no types.** So each rule needs a second signal before it reports. `no-effect-debounce` reports a timer in an effect only when the timer callback sets state. A delayed focus or a scroll passes.
- **The tests that matter are for code that must pass.** When a rule reports correct code, the fix goes into the rule. Step 3 explains why there's no other way out.

## Step 2: old code already breaks the rules

A new rule in an old code base has a problem on day one. On the day of the merge our code broke the rules in the baseline 26,332 times. One rule alone, the one that bans comments, had 14,123 of them.

<NumberBand value="26,332">
  violations of the rules in the baseline, in our code on the day of the merge. The 533 hidden ones from later in this post are counted separately.
</NumberBand>

Most of that number is not new decay. It's old code that was invisible before. One round of tightening, a day before the merge, took the record from 17,504 to 25,521 without a line of product code changing: test files stopped being exempt (type assertions went from 842 to 3,045), all 55 rules that were only warnings joined, and the per-file ceilings for complexity and file length, some as high as 4,000 lines, became counts too.

The two usual answers to "the code already breaks it" both fail.

- **Make the rule an error.** The build is red until someone fixes thousands of old lines, so the rule never merges.
- **Make the rule a warning.** The build is green and the count grows. I counted twice before the merge, 28 hours apart, and in between the main branch gained a net 181 (290 up, 109 down, in 36 files). Almost all of it was the comment rule: +187. New code still came with comments, because nothing stopped it.

A baseline is the third answer. I record how many times each file breaks each rule today, in one JSON file, and no count in it can go up. With a made-up path:

```json
{
  "no-type-assertion": {
    "src/features/billing/invoice.ts": 3
  }
}
```

One script lints the repository and compares the result with that file. The figure below cycles through the five cases that matter.

<RatchetLoop />

Case four is the one that is easy to miss. When a count falls and the record still allows the old value, the next person can add a violation back with no failure. So the record has to follow each count down, in the same pull request. It works like a committed offset in a log: it only moves forward.

For a pull request the rule is short: a file you don't touch costs nothing, and a file you touch can't gain a violation.

The output is written for a person and an agent alike. A rise names the file, the rule, both counts, the rule's message and each location. A fall names the command that locks it in. With made-up paths:

```text
✗ src/features/reports/report-table.tsx  no-comments  allowed 0, found 3
    Delete this comment and make the code say it: rename, extract a named function or constant, ...
    at 14:5, 31:3, 52:7
↓ src/features/reports/export.ts  no-type-assertion  allowed 4, found 3. Lock in the cleanup: run `just lint-ratchet --update` and commit the baseline.
```

Before the merge I put the new files of two other open pull requests on the branch. The check failed with 26 new violations in 9 files, and passed again without them.

### The allowlist that leaked

In August I'd done the first `useEffect` ban differently: the rule was off for a list of files that already had effects. That sounds reasonable, and it's how most teams roll out a strict rule. This is what the list did over the next eleven weeks:

<AllowlistLeak />

87 entries on 29 August, 109 by 16 November. Each new one was a one-line config edit that no check questioned, and once a file is on the list it can add as many effects as it likes. A list of exemptions can only grow. A count per file can only fall: after the merge, effects went from 197 to 194, in the same 102 files. The two panels summarise the argument of this post.

The August setup also had a commit hook that refuses a staged file with any warning in it, so whoever touches a file cleans it. That hook is still in place for those rules, and it works, but it has a price. In one performance sweep, 36 files already had 375 warnings between them. For 18 of them we dropped the edits, because a hoisted regex wasn't worth retyping a JSON parser to get the file clean. For the nine new rules, some with thousands of old cases, the baseline asks for less: don't make it worse.

## Step 3: close the ways around it

A check like this has two easy ways around it.

**Edit the number.** The script compares the allowed counts in the pull request with the allowed counts at the merge base, and refuses a number that's higher. The update command can only lower an entry or remove it. That's case five in the loop above.

In CI the checkout is the merge commit of the pull request, so its first parent is the main branch: the job checks out with `fetch-depth: 2` and passes `--base HEAD^1`. On a laptop the script uses the merge base with `origin/develop`. When CI can't find a base, the run fails, because a guard with nothing to compare against is no guard.

Three details keep the comparison fair:

- **A rename keeps its allowance.** A moved file inherits the count of its old path one time, from the renames that `git diff -M` reports. A new file at the old path starts at zero. This has already happened for real: on 21 November a teammate moved a workspace setup file into another folder, its allowance moved with it, and the total still fell by 41 in that change.
- **A new rule is seeded one time.** `--seed <rule>` records today's counts for a rule that the merge base doesn't list. It refuses a rule that already has a baseline.
- **A file can't trade a violation for a directive.** When the directive count of a file rises, its other counts stay as they were, and the update doesn't lower them. Otherwise an agent could silence a violation and record the "fall".

**Add a disable comment.** One `oxlint-disable-next-line` above the new violation silences the rule. So the script counts these comments from the source text, for each rule and each file, in every form: next line, same line, block, JSX and whole file. A new one fails the check. The first count found 338 that name a rule and 44 broad ones that name none. 57 of the named ones silenced nothing (rules that were never on, or a package where lint doesn't even run), so I deleted those. At the merge it was 284 named and 45 broad.

The first version had gaps. Three review rounds, each by a different model, tried to get past the check, and every round found something. The cases are below:

The first case is the most instructive. A blanket `/* oxlint-disable */` at the top of a file also switched off the rule that was supposed to catch blanket disables, so the run came back with zero diagnostics. Oxlint 1.91, the version in our repository, has no flag to ignore inline directives, which is why the script parses directives itself with the TypeScript parser. That takes about half a second for the whole repo.

An old disable comment leaves one more gap. It covers a range of lines, and a new violation inside that range isn't reported:

<HiddenMode />

A second mode of the script blanks each disable comment, lints again, and counts what shows up. On the day of the merge that was 533 hidden violations in 163 files. They live in the same record under their own keys, with the same rule: only down. This mode edits files while it runs, so it refuses to start when a file with a directive has uncommitted changes, and it runs in CI, not in the commit hook.

This is also why a false report must be fixed in the rule. The disable comment is closed as an exit, so the rule has to be right. The last round before the merge found three ways to pass `no-swallowed-error` without reading the error: `void error`, a bare `error;` statement, and an assignment to the caught variable. The rule reports all three now.

## One rule I deleted

In August I'd added a rule that asked for an `EFFECT:` comment on each effect, explaining why the effect had to exist. The November change deleted it, and the pull request said why in one line: "A comment must not make an effect acceptable."

A rule that accepts any effect with a comment above it has one pass condition, and that condition is the comment. Any author can write one in a few seconds, and the effect stays. The baseline counts the effects themselves, so a new effect fails unless the same file loses one. The price of an effect is paid in code now, not in prose. There are still 141 of those comments in the code (157 before the merge), and they're going away slowly as files get touched.

This is a change of position. The August post shows an `oxlint-disable-next-line` with a good reason after it as the right way to make an exception. In November a directive became a counted violation. I'd write the August post differently today.

## What it costs

- **On my machine,** a full run takes about 6 seconds, and the commit hook is about 5 seconds slower than before. Before the type-aware pass was added, the full run was under a second, so that pass is most of the cost.
- **In CI,** over 330 lint jobs on a standard two-core runner since 19 November, the baseline step has a median of 59 seconds and the hidden mode 83 seconds, so hidden mode adds about 24 seconds. In a small sample of the old lint job, the median went from 121 seconds before the merge to 241 seconds after it, so about two minutes longer.
- **On the day of the merge,** every open pull request is a risk. One that had passed its checks before the baseline existed merged 8 minutes after it, with 20 comments and one always-true condition in four files that the record allowed none or one. Every pull request that took the main branch then failed with lines like `allowed 0, found 11`. The fix removed the comments, gave one variable a longer name because a removed comment had explained it, and turned an always-true last branch into a plain `else`. The main branch was red for about 8 hours. I found it because my own next pull request failed, with 19 comments against 13 allowed, all from my own cache diagnostics.

One thing the automatic review warned about before the merge: two pull requests that lower the same count can race, and the second fails on a stale record. I didn't build the job that would fix that. It hasn't happened on the main branch since 19 November (43 push runs, 0 lint failures), but it can.

## Oxlint notes

Four behaviours of Oxlint are easy to miss when you write your own rules.

- **A wrong rule name is a parse error, and the run then reports zero findings.** That looks the same as a clean result. Check the exit code before you count.
- **A plugin turns on its complete `correctness` category**, not only the rules that you name.
- **The CLI flags `-D` and `-W` discard the rule options from the config file.** A rule with options must be set in a config file.
- **Selector rules do not exist.** Oxlint has no `no-restricted-syntax`, so each rule of that kind goes into a custom plugin.

One more, from a bulk fix. An automatic fix removed "useless" `undefined` from 16 places, including `mockResolvedValue(undefined)`. The 56 tests still passed, and 12 of the changes broke the type check, because the mocks were untyped and the test runner doesn't check types. We rewrote them as `mockImplementation(async () => {})`. Run the type check after a bulk fix.

## Set it up in another repository

Ours has 728 lines. This version keeps the core: the counts, the three failures, an update that only lowers, and the merge-base guard. With Oxlint 1.94.0 in a scratch repository, a new violation fails, a fix asks for the update, the update lowers the entry, and a count raised by hand fails.

```js
// baseline.mjs: node baseline.mjs [--seed | --update] [--base origin/main]
import { spawnSync } from "node:child_process";
import { existsSync, readFileSync, writeFileSync } from "node:fs";

const BASELINE = "lint-baseline.json";
const args = process.argv.slice(2);
const baseRef = args.includes("--base") ? args[args.indexOf("--base") + 1] : "origin/main";
const sh = (cmd, ...rest) => spawnSync(cmd, rest, { encoding: "utf8" }).stdout.trim();

const found = {};
for (const { code, filename } of JSON.parse(sh("npx", "oxlint", "-f", "json", ".")).diagnostics) {
  found[code] ??= {};
  found[code][filename] = (found[code][filename] ?? 0) + 1;
}
if (args.includes("--seed") && !existsSync(BASELINE)) {
  writeFileSync(BASELINE, JSON.stringify(found, null, 2) + "\n");
  process.exit(0);
}

const parse = (text) => (text ? JSON.parse(text) : {});
const allowed = parse(readFileSync(BASELINE, "utf8"));
const mergeBase = sh("git", "merge-base", "HEAD", baseRef);
const atBase = mergeBase ? parse(sh("git", "show", `${mergeBase}:${BASELINE}`)) : allowed;
const get = (map, rule, file) => map[rule]?.[file] ?? 0;

const errors = [];
const next = {};
for (const rule of new Set([...Object.keys(allowed), ...Object.keys(found)])) {
  const files = new Set([...Object.keys(allowed[rule] ?? {}), ...Object.keys(found[rule] ?? {})]);
  for (const file of files) {
    const [a, f, b] = [get(allowed, rule, file), get(found, rule, file), get(atBase, rule, file)];
    if (a > b) errors.push(`✗ ${file} ${rule}: baseline says ${a}, merge base says ${b}`);
    if (f > a) errors.push(`✗ ${file} ${rule}: allowed ${a}, found ${f}`);
    if (f < a) errors.push(`↓ ${file} ${rule}: allowed ${a}, found ${f}. Run with --update.`);
    if (Math.min(a, f) > 0) (next[rule] ??= {})[file] = Math.min(a, f);
  }
}
if (args.includes("--update")) writeFileSync(BASELINE, JSON.stringify(next, null, 2) + "\n");
console.log(errors.join("\n") || "Counts held.");
process.exit(errors.length > 0 && !args.includes("--update") ? 1 : 0);
```

The order I'd follow in another repository:

1. **Seed on the main branch, in its own pull request**, so that every later pull request has a merge base with counts.
2. **Run it in CI with a known base**: `fetch-depth: 2` and `--base HEAD^1`.
3. **Add it to the commit hook last**, and only if a full run takes seconds.
4. **Count disable comments before you announce it.** Otherwise the first answer to a red check is a new directive, and this short version can't see it.
5. **Merge it when few pull requests are open,** or tell people to rebase first. Ours broke the main branch 8 minutes after it landed.

The short version leaves out what our script added after real use: the rename rule, seeding of a single rule, the directive and hidden counts, the trade guard, and scoping to staged files for the hook.

## What I did not measure

- **The first drafts of the agents.** I count what reaches a commit. I don't know how many times an agent wrote a violation, read the error, and fixed it before committing.
- **A long trend.** The fall of 545 is from six days, and one pull request, which removed a sign-in method, is 108 of it. 21 November alone gave 219. Then the weekend was nearly flat. It's a start, not a rate.
- **Intent.** 142 of the 545 left with deleted files, and some of the rest came from pull requests that rewrote code for other reasons. The data shows violations falling in touched files. It doesn't show that people chose to clean.
- **The rule that bans comments.** `no-comments` was 14,123 of the 26,332, or 53.6%. That rule is our position. A team that keeps its comments would start with about half of this record.
- **August against November.** The November counts include test files and have no allowlists, so the two aren't the same scope. Six of the eight rules from the August table went down. Two went up over the wider scope: `prefer-nullish-coalescing` from 219 to 300, and `no-negated-condition` from 85 to 88.

Two items are still open as of 23 November. One rule reports correct code: `typescript/prefer-nullish-coalescing` flags `a?.trim() || b`, where an empty string must fall through. And a rule that becomes wider can't raise its own counts, because the merge-base guard refuses any raise, so a better rule needs a process that doesn't exist yet.
