On 8 October 2026, vLLM merged my pull request [#60497](https://github.com/vllm-project/vllm/pull/60497), which removes a quadratic list copy from the Python fallback detokenizer. The result comes in three parts, and they belong together:

- In a replay benchmark, CPU time for the fallback detokenizer fell from **7.46 s to 2.30 s** at 32,768 tokens per request, a 69% reduction.
- The replay runs on one CPU core with no model behind it, so it isolates the detokenizer.
- In live serving at 6,144 tokens per request, I measured no gain: the request time medians were 145.03 s and 145.23 s.

I give the second and third points the same weight as the first, because a component benchmark is easy to mistake for a serving result. The rest of this post explains the bug and the fix, how I found the problem, and what the measurements do and do not show.

## Background: incremental detokenization in vLLM

A serving engine cannot wait for a complete response before it produces text. vLLM converts token IDs to text while the model generates them, which is what makes streaming and stop-string checks possible. It cannot decode each token on its own, though, because the text of a token can depend on its neighbors: a leading space is one example, and a multi-byte character split across two tokens is another. So the detokenizer keeps a history and, on each step, decodes a short span around the new token.

vLLM has two implementations of this step and selects one for each request:

```python
if uses_fast_detokenizer(tokenizer):
    # Fast tokenizer => use tokenizers library DecodeStream.
    return FastIncrementalDetokenizer(tokenizer, request)

# Fall back to slow python-based incremental detokenization.
return SlowIncrementalDetokenizer(tokenizer, request)
```

`uses_fast_detokenizer` is a single check, `isinstance(tokenizer, TokenizersBackend)`. A tokenizer backed by the Hugging Face `tokenizers` library takes the fast path, which uses that library's `DecodeStream`. Everything else takes the fallback, `SlowIncrementalDetokenizer`, which is plain Python. vLLM's `MistralTokenizer` (tokenizer mode `mistral`) is one of those, and it is the tokenizer behind every measurement in this post.

Both implementations run in the API server process rather than in the engine process that drives the GPU. The fallback calls a helper, `detokenize_incrementally`, once for every output token, so any cost in that helper that depends on the output length is paid again on every step.

## The problem: a full-history copy on every step

`SlowIncrementalDetokenizer` keeps a Python list of token strings: a short tail of the prompt, followed by every output token so far. On each step it passes that list to the helper as `prev_tokens`, and before my change the helper began like this:

```python
output_tokens = prev_tokens + new_tokens
```

Concatenating two Python lists with `+` builds a new list and copies every element into it, so this one line copied the full token history on every decode step. The helper then read only the end of the copy:

```python
prefix_text = tokenizer.convert_tokens_to_string(
    output_tokens[prefix_offset:read_offset]
)
new_text = tokenizer.convert_tokens_to_string(output_tokens[prefix_offset:])
```

`prefix_offset` and `read_offset` point near the end of the list, which means everything before `prefix_offset` was copied and never read. A second branch handles tokenizers with added vocabulary, and it takes the same two slices.

<TokenWindow />

The cost of a step therefore grows with the number of tokens already produced. Over a response of N tokens the copies add up to about N²/2 list elements, which is negligible for a short reply and significant for a long one.

## How I found it

I did not find this with a profiler, and it did not start from a production incident. In the first week of October I began a general audit of vLLM's startup and request paths, looking for work that the engine could avoid. The first pass ran on an Apple Silicon Mac with no NVIDIA GPU, which limited it to reading source and measuring CPU-only paths.

The copy came out of that reading. A list concatenation inside a loop that runs once per token deserves a second look wherever it appears, and a microbenchmark confirmed the suspicion: with 32,768 tokens of history, one helper call took 52 µs, against 0.93 µs for a control with a bounded history.

Then I held the change back for two days, because the next measurement did not support it. A server test needs a model that actually uses the fallback path. Qwen takes the fast path in this vLLM version, so I used Ministral 3B, which uses the Mistral tokenizer, on a single L4 GPU. The responses matched and the detokenizer used less CPU time, but request time did not move. A lower component cost with no effect on requests was not enough to justify a pull request.

The profiling came after that, and its purpose was to explain why a real reduction in decode cost did not show up in the API process. It gave three answers:

1. **The copy cost grows quickly with output length.** At 6,144 tokens the saving is small. At 32,768 tokens it is most of the detokenizer's CPU time, as the results below show.
2. **The same loop has a second quadratic copy.** The output text is a Python string that grows by one token on each step. In an allocation profile of a single 16,384-token replay, that string accounted for about 1.11 GiB of cumulative allocation requests while peak tracked memory stayed near 1.2 MiB. An open pull request, [#36023](https://github.com/vllm-project/vllm/pull/36023), already covers it, so I left it alone.
3. **The API process does work for every engine output.** Both versions processed the same 6,145 output batches in the live test. Each batch is decoded and counted in metrics, even for a request that returns only a final result.

One of the profiles was wrong, and I discarded it. My first CPU-time profile used cProfile with a thread CPU clock, and it reported negative time for some functions. After I reproduced the same error in a script that had nothing to do with vLLM, I dropped that profile and repeated the measurement with yappi. The second profile passed its timing checks and pointed at three active areas in the API process: fallback decoding, Prometheus metric updates, and ZeroMQ event handling.

By then the correct claim was clear, and it was a narrow one. The change removes one of two quadratic copies. It cuts replay CPU time substantially for long outputs. It does not change request time at the load I tested. I opened the pull request with those three statements in its description.

## The fix

The helper now copies only the part of the history that it reads:

```python
output_token_count = len(prev_tokens) + len(new_tokens)
window_start = (
    0 if is_first_iter else min(prefix_offset, read_offset, len(prev_tokens))
)
output_tokens = (
    prev_tokens[window_start:] if window_start else prev_tokens
) + new_tokens
```

`window_start` is the earliest index that the slices can touch, and the copy starts there. Three details keep the behavior identical.

**The slice indexes shift.** The caller passes offsets that are positions in the full history, so inside the window each one moves left by `window_start`:

```python
prefix_text = tokenizer.convert_tokens_to_string(
    output_tokens[prefix_offset - window_start : read_offset - window_start]
)
new_text = tokenizer.convert_tokens_to_string(
    output_tokens[prefix_offset - window_start :]
)
```

**The returned read offset stays absolute.** The old code returned `len(output_tokens)`, which was the full token count. Because the window is now shorter than the history, the new code returns `output_token_count`, which it computes before the cut:

```python
return new_tokens, new_text, read_offset, output_token_count
```

The caller sees the same number as before.

**The first call keeps the prompt window.** A caller with no token history yet passes `prev_tokens=None`. In that case the helper converts the prompt tail itself and returns those tokens, and `window_start` is 0.

The window does not have a fixed size. When the decoded text ends in the replacement character `�`, the output has probably stopped in the middle of a multi-byte character, so the helper returns no text and leaves both offsets where they were. On the next step the window starts at the same index and is one token longer, and it keeps growing until the character is complete.

### Two errors in my first draft

A review of my own first draft turned up two errors, and both corrections are visible in the merged code.

- **An added copy.** The helper has two production callers, and one of them already trims its token history. For that caller the window starts at index 0, where my draft made a full slice copy before the concatenation. The merged code uses `prev_tokens` directly when `window_start` is 0.
- **A behavior change for unusual offsets.** A client can send offsets that point past the end of the token list. My draft emitted text in that case, while the original code emits none. The merged code caps `window_start` at `len(prev_tokens)`, and a new test covers the case.

The diff is 61 added lines and 7 removed across two files, and most of the additions are tests. The pull request description is explicit about the limit of the change: "Other copies in the caller remain."

## Validation

A detokenizer change that alters a single character of output is a bug, so I checked the output in three ways.

- **Live responses.** I ran both versions behind a real model, Ministral-3-3B-Instruct-2512 on one L4 GPU. All 24 baseline and patch response pairs matched in text, token IDs, finish and stop reasons, and usage.
- **Existing tests.** I ran the same test selection against the old helper and the new one. Each version passed 81 tokenizer tests and 94 renderer tests, with 91 existing skips, 660 deselected cases, and one expected failure.
- **New tests.** I added three cases, each run with both the GPT-2 and the Pixtral tokenizer: long Unicode output, the first-call prompt window, and offsets past the window.

This is the long-output case:

```python
def test_slow_decode_long_history_preserves_text_and_token_ids(tokenizer):
    truth = "A map.  我很感谢你的热情 🙂🌶️\n" * 32
    ids = tokenizer.encode(truth, add_special_tokens=False)
    text, output_ids = _run_incremental_decode(
        tokenizer, ids, skip_special_tokens=True, starting_index=0, fast=False
    )
    assert text == tokenizer.decode(ids, skip_special_tokens=True)
    assert output_ids == ids
```

The replay benchmark compares decoded text and token IDs between the two versions as well, and they match.

## Why serving did not get faster

The replay isolates the detokenizer; a deployment does not. For the live comparison I used Ministral-3-3B-Instruct-2512 on one L4 GPU, with four requests of 6,144 tokens each.

- The request time medians were 145.03 s and 145.23 s.
- The API CPU medians were 4.64 s and 4.765 s, with overlapping ranges.

Neither is a gain, and the pull request says so: the 69% claim applies to the replay only.

The replay numbers explain why. At 8,192 tokens the fix saved 0.34 s of CPU time across four requests. The live requests were shorter than that, and each took about 145 s, so at this length GPU time is far larger than detokenizer time. The API CPU median stayed below 5 s in both versions, in a run where a single request took more than two minutes.

## When the change should matter

The fix removes work that grows with the square of the output length, in the process that serves the API. I expect it to matter when these conditions hold:

- **Long outputs.** At 32,768 tokens, the replay saved 5.16 s of CPU time across four requests.
- **Many concurrent streams.** Each stream has its own detokenizer, and all of them draw on the CPU time of the API process.
- **An API process that is short on CPU.** With spare CPU, a shorter detokenizer step changes little.

I did not measure any of these conditions in serving, so the only result I claim is the replay number.

## How to check your own deployment

1. **Find which detokenizer path your tokenizer uses.** The decision is this function in `vllm/v1/engine/detokenizer.py`:

   ```python
   def uses_fast_detokenizer(tokenizer: TokenizerLike) -> bool:
       """Whether the engine detokenizes with `FastIncrementalDetokenizer`."""
       return isinstance(tokenizer, TokenizersBackend)
   ```

   If your tokenizer is not a `TokenizersBackend`, your requests use the fallback.

2. **Check whether your version has the fix.** Search `vllm/tokenizers/detokenizer_utils.py` for `window_start`. The fix merged to `main` on 8 October 2026.

3. **Profile the API server under load.** Attach a sampling profiler to the API server process while it serves long outputs. With py-spy:

   ```bash
   py-spy record --pid <api-server-pid> --duration 60 -o profile.svg
   ```

4. **Look for time that grows with output length.** Find `detokenize_incrementally` and `SlowIncrementalDetokenizer.decode_next` in the profile, then record one run with short outputs and one with long outputs. If the share of CPU time in those two functions rises with the output length, you have this problem. If the API process is mostly idle, the detokenizer is not your bottleneck.
