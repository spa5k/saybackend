Claude Code 2.1.323, released on November 12, 2026, added Code Mode. With it on, Claude does not ask for `Read`, `Bash` or an MCP tool one call at a time. It writes JavaScript, and Claude Code runs that script inside its own process. Every tool call the script makes still goes through the permission rules and hooks under the tool's usual name.

The [first post in this series](/blog/code-mode-explained/) covers the idea. This one covers Claude Code's version: how to turn it on, what the shipped bundle shows about the runtime and its limits, how a script fails, and what it did on a ten-call MCP task. The measurements ran on 2.1.329. The current `latest` release is 2.1.330, whose Code Mode changes are bug fixes. Its bundle has the same limits as below.

## Turn it on

Code Mode is experimental and off by default. One environment variable turns it on:

```bash
claude --version   # 2.1.323 or later
CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude
```

To keep it on, put the variable in the `env` block of `~/.claude/settings.json`. Claude Code ignores it in a project's settings files, so a cloned repository cannot switch it on. The value `0` in managed settings blocks it for an organization.

The first start asks for confirmation. After **Yes, turn on Code Mode**, Claude Code restarts and prints this line:

```text
Code Mode (experimental) is on · this session can be resumed only with Code Mode on
```

The requirements are narrow. It needs the native build, an interactive terminal, a direct Claude API or subscription login, and Opus 5.5, Sonnet 5.5, Haiku 5.5 or Fable 5.2. Bedrock and the other cloud providers, gateways, a custom `ANTHROPIC_BASE_URL`, an API key helper and OpenTelemetry tracing all keep it off. The `stable` release channel is at 2.1.323, the first release with Code Mode, so stable users get it without the many fixes of the releases after it.

Print mode is also out. `claude -p` with the variable set starts with the ordinary tools and writes this to stderr:

```text
Warning: Code Mode (experimental) isn't available: for now it only works in the interactive terminal. Starting with the ordinary tools.
```

I got the same refusal in a real terminal when the shell had inherited `CLAUDE_CODE_ENTRYPOINT` from another agent tool. Starting Claude Code from a clean environment fixed it.

The feature changes fast. The changelog has 52 Code Mode entries in the five releases after 2.1.323.

## One tool, called REPL

Code Mode replaces direct tool calls with one tool. Its name in the bundle and in permission rules is `REPL`, and the terminal shows it as **Code**. The input schema has three fields:

- `code`: "JavaScript code to execute. Supports top-level await. State persists across calls."
- `description`: a 5 to 10 word summary.
- `timeout`: "Optional limit on the script's own running time in milliseconds; time spent inside the tool calls it awaits is not counted (default 30000, max 600000)".

The npm package `@anthropic-ai/claude-code` is now a wrapper around a 360 MB native binary, so I read the prompt text and the runtime with `strings`. The binary is built with Bun 1.4.4, so the JavaScript engine is JavaScriptCore, not V8. The script does not run in a child process or a container. Claude Code transpiles it with `Bun.Transpiler` and runs it in a `vm` context in its own process. The context is created with string code generation and WebAssembly off, so `eval` and `new Function` do not work either. The tool prompt says it directly:

> There is no `import`, `require` or `process`: the context is sealed, and the globals below are how it reaches the machine. The REPL language is always JavaScript, whatever the codebase is written in — run the codebase's own tools (pytest, cargo, go test, …) with `$`.

The globals are the tool API. `$` is a template tag for shell commands, which become `Bash` calls. `edit()` and `write()` change files. `self.log()` adds a line to the output that Claude reads. `preview()` cuts a long value. `searchTools()`, `describeTool()` and `tools.list()` find tools, and `tools.mcp__server__tool(input)` calls one, MCP tools included. Variables stay in the context between scripts, but not across a restart or a resume.

The bundle carries two versions of the paragraph that tells Claude what a call costs. One of them reads:

> What a `REPL` call costs: each call is a full model round-trip — the whole conversation is re-read before your script runs, and you wait for the reply — while the work inside a script (shell commands, file reads, searches, tool calls) is comparatively free, and runs concurrently when you fan it out with `Promise.all`.

## The limits in the bundle

These constants sit next to the REPL runtime in 2.1.329 and 2.1.330:

- A script that Claude waits for stops after 10 minutes (600,000 ms) of wall-clock time. In auto and `bypassPermissions` modes a script can move to the background, and there the limit is 2 hours (7,200,000 ms).
- The script's own running time, without tool calls, defaults to 30 seconds and can be raised to 10 minutes with `timeout`.
- After about 30 seconds a running script detaches and the next script starts beside it. The two share variables.
- One script can make at most 50,000 tool calls. Call number 50,001 throws "this script has made 50,000 calls, its cap. The call was not made, and no later call of this script will be answered."
- The transpiler puts a step counter into the code. The budget is 300,000,000 steps per turn, where a step is one pass through a loop or one call of a function, and a turn is the code that runs between two awaited tool results or timers.
- Memory growth is stopped at a quarter of the machine's memory, with a floor of 1 GiB and a ceiling of 4 GiB. Before 2.1.329, a runaway loop in a script could fill the machine's memory.
- A read of a line range over 256 MiB is refused.
- An MCP call inside a script waits up to 10 minutes and then fails with an error. Before 2.1.329, a call that took over two minutes returned a "moved to the background" message as if it were data.

The step budget being per turn matters for long scripts. A loop that awaits a tool call on every pass resets the counter each time, so it is bounded by the 30-second script time, the wall clock and the call cap, not by the steps. The steps stop only code that never yields, which is the case a timer cannot catch.

## How a script fails

A script's result has its return value, the `self.log` lines, and notes that Claude Code adds about calls that did not go as planned. The note texts are in the bundle, and the ones a model meets most often are these.

- **A refused call.** It shows under "Tool calls that were refused while this script ran:", one line each, with "and N more refused calls" past a limit. A call refused after the script returned goes under a second heading, "Tool calls that were refused after this script returned:".
- **A call the script forgot to await.** When the script ends first, Claude reads that the call "had not started when the script ended, and did not run" or that it was "still running when the script ended. They have since finished or moved to the background, where they may still be running, but the script ended before their results came". Both end with "Add 'await'", and the second also says "Do not make them again."
- **A call still running when the script failed.** Since 2.1.328, Claude is told which ones they were.
- **A forgotten call that then fails.** Its error is listed with the script's error, with the note that it "did not cause" it.

The second case is the one to know when comparing agents. pi and OpenCode abort the calls a finished script left running. Claude Code lets them finish and tells the model not to repeat them. For writes that is the safer default, because a cancelled write may have landed anyway.

Output has caps too. A single log line over 1 MiB keeps its start and end around "[N characters of this console line were not kept]", and captured console output stops at 50 MB with "[console output truncated at 50MB]".

Variables that persist between scripts are the other source of surprises, and the changelog shows how many edge cases that has. 2.1.328 fixed top-level variables that an earlier failed script never set being silently `undefined`. 2.1.329 fixed `let x;` keeping the value an earlier script gave `x`, and fixed scripts losing `tools` in sessions with more than 4,096 tools. State in a long-lived context is convenient for the model, and it is also where a script can read a value that a different script left behind.

## What I measured

I wrote a stdio MCP server in Node with 20 mock tools for a small shop: orders, customers, invoices, stock and so on. `get_order` returns about 1,250 characters of JSON with a `next_order_id`. The ten orders in the chain are not in id order, so the only way to the answer is to follow the chain one call at a time.

The server goes in `mcp.json`:

```json
{ "mcpServers": { "mock": { "type": "stdio", "command": "node", "args": ["/abs/path/mock-mcp.mjs"] } } }
```

`settings.json` allows the server's tools and adds a `PreToolUse` hook that logs every call:

```json
{
  "permissions": { "allow": ["mcp__mock"] },
  "hooks": {
    "PreToolUse": [
      { "matcher": "*", "hooks": [{ "type": "command", "command": "node /abs/path/hook-log.mjs /abs/path/hook.log" }] }
    ]
  }
}
```

```bash
CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1 claude --model haiku --permission-mode default \
  --setting-sources local --settings settings.json \
  --mcp-config mcp.json --strict-mcp-config
```

Because Code Mode needs a terminal, I drove the session through tmux and read the token counts from the session transcript in `~/.claude/projects/`. The prompt was the same in every run:

```text
Use the tools of the "mock" MCP server. Start with order O-1. Each order has a next_order_id.
Follow the chain until next_order_id is null, and reply with the sum of the total fields of
every order in the chain. Reply with only the number.
```

All six runs answered 1603.75, which is correct. With Code Mode on, Haiku 5.5 first searched for the tool, for example with `searchTools("order", 20)`. In the first run it then wrote this script:

```javascript
const seen = [];
let id = "O-1";
const orders = {};
while (id !== null && id !== undefined) {
  if (seen.includes(id)) throw new Error("cycle at " + id);
  const o = await tools.mcp__mock__get_order({ id });
  orders[id] = o;
  seen.push(id);
  id = o.next_order_id;
}
self.log(JSON.stringify(orders, null, 2));
```

The ten calls ran inside one REPL call, and the hook log shows them 40 ms apart. With Code Mode off, Claude made one `ToolSearch` request and then one request per order.

The cause is the re-reading. With Code Mode off, each of the 12 requests read the whole conversation again. In the median run that grew from 37,346 tokens at the first request to 45,190 at the last. With it on, there were three requests: find the tool, run the script, answer.

Two other numbers moved. The first request was smaller with Code Mode on, 21,091 tokens against 37,342, because one REPL tool replaces the definitions of the built-in tools. Output fell from 948 to 562 tokens at the median. Most of the input was cache reads in both settings, so the bill moves less than the token count: 478,275 cached tokens with the flag off, 59,700 with it on.

Code Mode does not stop a model from printing too much. In two of the three runs, Haiku sent all ten full orders back into its context, about 7,000 tokens, where ten numbers were enough. In the third it logged only the id, total and next id of each order, and its last request grew by 736 tokens.

I also ran a task with independent calls: list ten orders, fetch each, sum. That is one run per setting, so read it as a direction. With the flag off, Haiku asked for all ten `get_order` calls in one message, so both settings took four requests. Code Mode still read less, 96,373 input tokens against 158,074, because its prompt is smaller. The wall-clock time did not improve.

## Permissions and hooks, per call

The hook log of a Code Mode chain run had 12 entries: two for `REPL` and ten for `mcp__mock__get_order`, each with its own `{"id": ...}` input. The `searchTools` calls did not reach the hook. The `REPL` entry carries the whole script in `tool_input.code`, so a hook can inspect the code before it runs.

For a deny rule that matches some calls and not others, I added `"deny": ["Bash(touch *)"]` and asked for one script that runs `echo one`, `touch denied.txt` and `echo two`. The hook saw all three commands. The middle one was refused and the script went on. The script's result for that command was:

```text
exitCode: 1
error: 'Permission denied for Bash: Permission to use Bash with command touch denied.txt has been denied.'
```

The REPL result also listed it under "Tool calls that were refused while this script ran", and `denied.txt` was not created.

A deny rule on a whole MCP tool works differently: the tool is removed. With `"deny": ["mcp__mock__get_customer"]`, Claude's script got this from `describeTool`:

```text
describeTool: no tool named mcp__mock__get_customer. searchTools('words') finds one.
```

With the flag off, the same rule made `ToolSearch` return "No matching deferred tools found." In both settings the tool does not exist for Claude.

Three parts of the model are new:

- **Auto mode** reviews each script once, before it runs, and not each tool call. The classifier cannot see values that the script computes, such as a path taken from search output. Rules and hooks still run per call.
- **`ask: ["REPL"]`** asks for approval of every script before it starts.
- **The sandbox** covers the shell commands a script runs. The JavaScript and its file, web and MCP calls run outside it, in the Claude Code process.

Output checks moved too. A `PostToolUse` hook that matches `REPL` can rewrite what Claude reads through `updatedToolOutput`. Since 2.1.328, `UserPromptSubmit` hooks no longer receive script output. Since 2.1.329, a `PreToolUse` hook that errors no longer refuses a script's call; set `"onFailure": "block"` on a hook that must refuse.

## How it differs from programmatic tool calling

The Claude API has a related feature, programmatic tool calling. There, Claude writes Python that runs in an Anthropic code execution container. Tools opt in with `allowed_callers`, and each call pauses the code until your application returns a `tool_result`. MCP connector tools cannot be called that way.

Code Mode is the local counterpart. The language is JavaScript, the host is the Claude Code process, and every tool the session has is callable, MCP servers included. Your permission rules and hooks are the place to put checks, because Claude Code runs each call itself.

The time limits differ in the same direction. A programmatic call that your application does not answer in about 4 minutes raises a `TimeoutError` inside the Python, and each cell has 90 seconds of wall clock. A Code Mode script has 30 seconds of its own running time, 10 minutes of wall clock in the foreground, and an MCP call inside it waits up to 10 minutes. Time spent waiting on a permission prompt, a plan approval or an MCP form does not count toward the 10 minutes since 2.1.328 and 2.1.329. On the API side your tools must answer within minutes; in Code Mode a slow approval does not kill the script.

## When to leave it off

Code Mode earns its keep on chains of dependent calls, where it removed 9 of 12 model requests in my runs. On the parallel task it read less input but took slightly longer, so for work that the model already batches in one message the gain is the smaller prompt, not the wall clock.

The costs are in control and in operations. Auto mode reviews the script once, so a destructive call whose target the script computes is judged on the code, not on the value. The sandbox setting covers only the shell commands a script runs; file edits, web fetches and MCP calls from the script run in the Claude Code process with its full rights, which is the same as outside Code Mode but easier to forget when one tool call does 200 things. A session started with Code Mode can be resumed only with it on. And the feature is young: the stable channel has 2.1.323, while the releases since have fixed scripts that held earlier values, lost tools or ran into the ten-minute limit during a prompt. For a team, the managed setting `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=0` keeps it off until the fixes reach stable.
