Every coding agent I run in parallel gets its own git worktree. `git worktree add` writes every tracked file again, and the install or build that follows writes more. With twenty agents on one laptop, that is twenty copies of the same bytes.

[git-twig](https://github.com/leostera/git-twig), by leostera, makes the worktree from filesystem clones instead. Version 0.5.0 came out on 17 November 2026. This post is part 3 of "Rust on a laptop". [Part 1](/blog/rust-target-directory-disk-space/) shows where the disk under `target/` goes, and [part 2](/blog/rust-build-cache-worktrees-mbx/) shares one build cache across worktrees with mbx. This part is not only about Rust: one of the two test repositories is the Vite monorepo.

## Copy-on-write in four commands

On APFS, `cp -c` calls `clonefile(2)`. The new file gets its own inode but points at the same data blocks as the original. A block is copied only when one of the two files writes to it.

`du` adds up the size of every file, so it counts a clone twice. To see real use, I measure on a separate APFS volume and read its "Volume Used Space", which `diskutil` gives in bytes:

```sh
diskutil image create blank --fs APFS --size 2G --volumeName cowtest cowtest.asif
diskutil image attach cowtest.asif          # mounts /Volumes/cowtest
cd /Volumes/cowtest
used() { sync; diskutil info /Volumes/cowtest | grep 'Volume Used Space'; }

head -c 1073741824 /dev/urandom > big.bin
cp -c big.bin clone.bin; used
du -sh .
head -c 1048576 /dev/urandom | dd of=clone.bin bs=1m conv=notrunc; used
```

```text
   Volume Used Space:         1.1 GB (1073766400 Bytes) (exactly 2097200 512-Byte-Units)
2.0G	.
   Volume Used Space:         1.1 GB (1074814976 Bytes) (exactly 2099248 512-Byte-Units)
```

The clone costs nothing, `du` reports 2 GB for 1 GiB of data, and a 1 MiB write into the clone adds exactly 1,048,576 bytes. Read the number twice after a large write, because it moves for a second while APFS settles. A separate volume matters: on the boot volume, the used space also moves with every other program that writes. Every disk number below comes from this method, on a 60 GB image used only for this test. `hdiutil detach /Volumes/cowtest` removes the demo volume.

## What git twig new does

```sh
cargo install git-twig --locked    # Rust 1.95+ and Git 2.40+
git -C main twig new -b feat-x ../feat-x HEAD
```

I read the v0.5.0 source; the crate on crates.io is the same code as the `v0.5.0` tag. `git twig new -b <branch> <path> [<commit>]` (or `--detach`) runs these steps:

1. Build the target index in private staging under `.git/twigs/staging` with `git read-tree <commit>`. The staging directory must be on the same filesystem as the destination.
2. Pick a donor: up to five registered worktrees on the same device, the main checkout first. The donor is the one whose `HEAD` tree has the most paths with the same blob ID as the target.
3. Clone. On macOS each top-level tracked directory is one `clonefile` call, and then every entry that is not in the target tree is deleted. On Linux it walks the tracked files and clones each with `FICLONE`.
4. Verify. Every cloned file goes through `git hash-object` with no filters and must equal the target blob. Files that fail, and files with no donor match, are written by `git checkout-index`.
5. Register with `git worktree add --no-checkout`, move the staged files in, write a fresh index with `git read-tree`, and run the `post-checkout` hook.

So only committed, tracked files are shared. A dirty file in the donor is rewritten by Git, and ignored files such as `node_modules/` and `target/` do not reach the new worktree. The index is new, not cloned. `git twig list`, `remove`, `prune` and the other subcommands pass straight to `git worktree`.

Anything outside that path falls back to plain `git worktree add`: an omitted `-b`, options like `-B` or `--lock`, sparse checkout, `GIT_DIR` and similar overrides, replace refs, and a `reference-transaction` or `post-index-change` hook. With `TWIG_TRACE=1` it prints what it did:

```text
git-twig: donor: ".../js/main", 3016 matching target paths
git-twig: APFS directory clones: 6
git-twig: checkout: 3011 verified file clones, 0 Git-written paths
git-twig: native preparation: snapshot 0.514s; raw verification/repair 1.414s; total 2.195s
```

## Which files get cloned

Step 4 decides file by file, and the decision depends on `.gitattributes`. A clone is only correct when the working file must hold exactly the bytes of the blob, so git-twig asks `git check-attr` for every path before it clones anything ([`checkout.rs`](https://github.com/leostera/git-twig/blob/v0.5.0/crates/git-twig/src/checkout.rs)):

- A file with no conversion, `eol=lf`, or `text=auto` under the default `core.autocrlf=false` is cloned and verified.
- A file with `eol=crlf`, `ident`, `working-tree-encoding` or the old `crlf` attribute is written by `git checkout-index`, because Git changes its bytes on checkout.
- Any `filter` attribute stops the fast path for the whole worktree. git-twig will not run an external program in its private staging and then again in the fallback.
- A submodule, `core.symlinks=false`, replace refs or grafts also fall back to stock Git.

The `filter` rule matters most, because Git LFS works through `filter=lfs`. I added one LFS line for `*.md` to a copy of ripgrep and ran `git twig new` with tracing:

```text
git-twig: stock Git: checkout attribute filter="lfs" on ".github/ISSUE_TEMPLATE/feature_request.md" requires stock Git
```

One LFS pattern anywhere in the repository turns every `git twig new` into a plain `git worktree add`. Line-ending rules cost less. With `*.rs text eol=crlf`, the same repository gave `125 verified file clones, 102 Git-written paths`: the 102 Rust files got their CRLF copies from Git, and everything else was cloned.

The user's Git config counts as much as the repository. With `core.autocrlf=true`, the default choice of the Git for Windows installer, every text file needs conversion on checkout, and only files that contain a NUL byte, which Git treats as binary, can be cloned. On plain ripgrep with no `.gitattributes`, `git -c core.autocrlf=true twig new` gave `8 verified file clones, 218 Git-written paths`, so almost nothing was shared. With `core.autocrlf=input`, which converts only on commit, all 226 regular files were cloned. `git config --show-origin core.autocrlf` shows where the setting comes from.

Verification is the slow part of creation. It runs `git hash-object --no-filters --stdin-paths` over the cloned files, with up to four workers in parallel, but only when there are at least 512 files and 64 MiB of data ([`objects.rs`](https://github.com/leostera/git-twig/blob/v0.5.0/crates/git-twig/src/objects.rs)). Vite's 18 MB gets one worker, which is why verification took 1.4 s of the 2.2 s in the trace above.

## The test

The machine is an Apple M4 with macOS 27.2.1. The tools are Git 2.56.1 (built from source), git-twig 0.5.0, Rust 1.100.0, Node 26.13.1 and pnpm 12.21.0.

- **Vite** at commit `3567471`: 3,016 tracked files, 18.0 MB. `node_modules` installed with pnpm, the store on the same volume.
- **ripgrep** at commit `4d592f1`: 227 tracked files, 3.3 MB. A debug `cargo build` makes a 296 MB `target/`.

For each method a script makes 20 worktrees from the main checkout, one after another, and reads the volume after 1, 5 and 20. A second run of the plain methods gave the same numbers to within 0.1%. The methods:

- `git worktree add -b <name> <path> HEAD`, alone and followed by `pnpm install --offline` or `cargo build`.
- `git twig new -b <name> <path> HEAD`, alone and with the same install. For ripgrep, `cp -c -R main/target` into the worktree and then `cargo build`.
- `cp -c -R main <path>`, a clone of the whole checkout with `.git`, `node_modules` and `target/`. This is a separate repository, not a worktree, but it is the baseline for "clone everything".

A Vite worktree from `git worktree add` costs 30.4 MB, more than its 18 MB of files, because every file fills whole 4 KiB blocks and each file and directory needs metadata. A `git twig` worktree costs 1.9 MB: a 0.38 MB index plus the metadata of 3,016 files and their directories. Twenty of them use 38 MB, about what one plain worktree uses.

ripgrep shows the same ratio at a smaller size: 4.06 MB for `git worktree add` and 0.15 MB for `git twig`, so twenty twig worktrees (3.0 MB) use less than one plain worktree.

The dependencies add the same amount in both cases. pnpm on macOS already clones packages from its store, so the files in `node_modules` are almost free in both cases. Each install still adds about 20 MB of directories, symlinks and metadata, and takes about 7 seconds. `cp -c -R` of the whole checkout, with `node_modules` and `.git`, uses 16.4 MB per copy, less than one `git worktree add`, because a clone of a file costs only its metadata.

For Rust the tracked files are small and `target/` is not: a fresh `cargo build` adds 297 MB to every worktree. git-twig does not touch `target/`, but it changes what a cloned `target/` is worth:

```sh
git -C main twig new -b agent-7 ../agent-7 HEAD
cp -c -R main/target agent-7/target
cargo build --manifest-path agent-7/Cargo.toml
```

In a twig worktree the copy and the build take 0.65 s together, and Cargo compiles nothing. In a `git worktree add` worktree the same steps take 5.0 s, rebuild the 9 workspace crates and add 162 MB. The cause is the modification time. Cargo compares source mtimes with its build records, and `clonefile` keeps the donor's mtime: a cloned file showed `Nov 21 04:11:36`, the time of the original checkout, while Git's copy showed `06:35:18`, the time it was written. Crates from the registry are not affected, because their sources are outside the worktree.

## With mbx

The two tools split the work: git-twig shares the tracked files, and mbx shares the build output. mbx does not depend on modification times, because its keys come from file contents, and it gives every worktree its own managed `target/` made of clones from its store. I put the mdBook repository from part 2 and the mbx cache on a fresh APFS volume, built the main checkout once with `mbx build`, and then created four more worktrees on the same commit, each followed by `mbx build`:

Every build restored all 8 workspace crates from the store and took 1.5 to 1.9 s. A worktree with a complete debug build of a 262-package project cost 1.8 MB. For parallel agents this is the combination to start from: the first build of a commit pays in full, and each further worktree costs a few seconds and a few megabytes.

Cleanup works across the two as well. `git twig remove` deletes the worktree, and mbx collects a managed target once its checkout is gone, at its next collection run. Until then the target still counts against mbx's budget in logical bytes, though on APFS it holds almost no blocks of its own.

git-twig is slower to create: 1.15 s against 0.56 s for Vite, 0.31 s against 0.07 s for ripgrep. It runs Git several times, hashes every cloned file, and then registers the worktree, where `git worktree add` runs one checkout. Next to an install or a build the difference disappears, and for ripgrep the twig path with a cloned `target/` is the fastest way to a built worktree.

## How the saving decays

A clone shares blocks only until something writes the file. I took one twig Vite worktree (1.9 MB) and changed it step by step:

The checkout back to HEAD does not restore the sharing: Git writes new files, even though their bytes equal the donor's. A formatter, a code generator or an editor that saves by rename does the same, and `git status` then shows no change at all while the worktree costs as much as a plain one. In ripgrep, editing the `rg` binary crate and rebuilding added 63 MB, and editing `grep-searcher` added 25 MB.

A new worktree on another branch or an old commit shares only the files that match. Version 0.5.0 picks the donor with the most matching blobs. With only the main checkout to choose from, a twig worktree at `HEAD~300` cloned 2,414 files and let Git write 395, for 7.1 MB against 29.1 MB from `git worktree add`. At `HEAD~1000`, nine months older, it cloned 1,836 and wrote 703, for 8.7 MB against 26.3 MB.

## Removal, gc and prune

`git twig remove` frees only the private blocks: 1.9 MB for a worktree that `du` reports as 27.7 MB. Deleting a worktree directory and then running `git worktree prune -v` prints `Removing worktrees/<name>: gitdir file points to non-existent location`, the same as for any linked worktree. `git gc --prune=now` in the main checkout left the twig worktrees clean: `git status` and `git fsck` reported nothing. The clones are working files, not Git objects, so gc does not see them. After every successful creation, `.git/twigs/staging` was empty.

`git twig adopt` is experimental in 0.5.0. On a plain worktree, `adopt --dry-run` reported `matched_files=2660 matched_logical_bytes=17923990 skipped_files=356 kernel_deduped_bytes=0; physical savings NOT measured`. `--prepare` wrote its 2,660 candidates as verified clones into `.git/twig-adopt-prototype-*` and left them there, without replacing a file. `--dedupe` on APFS stops with `in-place adoption is Linux-only; APFS live file replacement is intentionally unsupported`. In this release adopt does not reclaim space on macOS.

## Silent fallbacks

A fallback is not an error. Without `TWIG_TRACE=1`, git-twig prints nothing about it and creates a plain worktree, so the only sign is the disk. I asked for a twig worktree on a second APFS volume, with the repository on the boot volume:

```text
git-twig: stock Git: Git metadata and destination are on different filesystems
```

The worktree was registered and complete, at full size. The same thing happens with the filters above, with an option such as `--lock`, and on a filesystem without reflinks. Run one creation with tracing in each new repository or machine before you rely on the numbers in this post. For a script or an agent harness, the trace also makes a cheap check: a line that starts with `git-twig: stock Git:` means the worktree is a plain one, and the rest of the line says why.

## On Linux

On Linux git-twig walks the tracked files and clones each one with the `FICLONE` ioctl, because that call works on single files and not on directories ([`snapshot.rs`](https://github.com/leostera/git-twig/blob/v0.5.0/crates/git-twig/src/snapshot.rs)). XFS with reflinks and Btrfs support it; ext4 does not. I ran the ripgrep test in a privileged `rust:1.100.0-trixie` container (Git 2.47.3), on two 3 GB loop devices, one formatted `mkfs.xfs -m reflink=1` and one `mkfs.ext4`, and read `df` before and after 20 worktrees:

## The alternatives I tested

- `git clone --shared`, `--local` and `--reference` share objects, not the working tree. Each Vite clone used 30.6 MB, the same as `git worktree add`.
- Sparse checkout cuts the files themselves: a worktree with only `packages/vite` (649 files) used 6.3 MB. git-twig does not combine with it; from a sparse worktree it falls back with `sparse checkout requires stock Git`.
- `jj workspace add` in jj 0.47.1 wrote a full working copy: 31.0 MB.
- A pnpm store on the same disk already makes `node_modules` cheap on macOS. For build output, a shared cache is the alternative to cloning `target/`.

## The trade

- Creation is 2.1 to 4.7 times slower for the files alone.
- It needs APFS, Btrfs or XFS with reflinks, with the repository, its `.git` and the new worktree on one filesystem. On ext4 or NTFS you get plain `git worktree add`.
- Only `-b` and `--detach` take the fast path. An app that calls `git worktree add` itself gets no saving; `git twig skill` prints instructions that tell an agent to call `git twig new`.
- A `filter` attribute anywhere, such as Git LFS, disables it for the whole repository.
- `core.autocrlf=true` in the user's config, or `eol=crlf` in `.gitattributes`, makes Git write the affected files instead of cloning them.
- A fallback prints nothing unless `TWIG_TRACE=1` is set, so a misconfigured machine looks like it works and uses full disk.
- Only tracked, committed files are shared. Dependencies and build output need their own plan.
- Clones diverge as files are written, and the sharing does not come back.
- `du` reports the full size of every clone. Measure on a separate volume.
- A failed creation keeps its staging directory and can leave a registered, partial worktree. Inspect it before you retry.
