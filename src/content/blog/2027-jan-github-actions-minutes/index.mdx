GitHub bills each job on a hosted runner for at least one full minute. A job that runs for 9 seconds costs one minute. In our monorepo at work, many jobs finished in seconds and ran very often, and November 2026 was on track for about 110,000 minutes.

In early November I made changes that should remove about 30,000 of those minutes each month, which is about 27%. Two things to know about that number:

- **The rule is real.** GitHub's [pricing page](https://docs.github.com/en/billing/reference/actions-runner-pricing) says: "GitHub rounds the minutes and partial minutes each job uses up to the nearest whole minute."
- **The saving is a projection.** This post has no measured number for the weeks after the change.

Most rows have one shape: a short job that ran more often than its result could change. The largest row is one workflow with three triggers.

## The rule: count jobs, not seconds

The cost of a job is its duration rounded up to a whole minute. The cost of a workflow is the sum over its jobs, and each job is rounded on its own.

That changes what to look for. Five jobs of 10 seconds are 5 billed minutes. The same five commands as steps of one job are 1 billed minute. A job that takes 25 minutes and runs twice a day is not the problem. A job that takes 9 seconds and runs after every push is.

So the number to watch is jobs multiplied by frequency, and the list to read is the workflows that run most often, sorted by job count.

## The largest row: one workflow, three triggers

On 29 October I added a merge policy workflow. Feature pull requests into the development branch must be squashed, and back-merges from the production branch must be merge commits made by the CI bot. The workflow enforced that routing and merged the back-merges itself.

It had three triggers: pull request events, the end of every CI run, and a schedule every 10 minutes (`*/10 * * * *`). The scheduled sweep read the status of every open pull request. With 81 open pull requests it took 74 seconds, so each sweep was billed as 2 minutes.

Derived from those two numbers: a sweep every 10 minutes is 144 sweeps a day, and at 2 billed minutes each that is 288 minutes a day, or about 8,640 minutes in 30 days. That is the sweep alone, without the job after every CI run.

All of this routed and merged about 8 back-merges a month. I project about 18,000 minutes a month for the workflow, which is about 2,250 minutes for each back-merge (18,000 divided by 8).

On 6 November I removed it.

The rows do not sum to the headline. Without the test row they sum to 26,050. With it they sum to between 31,050 and 36,050. I use about 30,000 as the total. None of these is a measurement, and the Terraform row and the test row rest on 20 hours of usage on the main branch.

Most rows have the same shape as the merge policy: a short job with a trigger that fires more often than its result can change. A login comment that does not depend on the commit does not need a run for each commit. A cleanup sweep that backs up an immediate cleanup does not need to run each hour.

### Affected tests only

This row is different, because it trades coverage for minutes. Pull requests into the development branch now run only the unit and integration test files that import a changed file:

```bash
vitest --changed=HEAD^1
```

Vitest cannot trace every kind of change, so some changes still run the full suites: dependencies and workspace packages, the Vitest config, the test database setup, the integration setup file, and files that are not code, such as migrations and fixtures. Release pull requests and every push to the development branch run everything.

The estimate comes from a small sample. In 6 recent pull requests, half selected few or no tests. Before the change, each of them ran all 6 shards.

The risk is specific. A test that reads a file from disk, where that file is not on the full-run list, can be skipped on a pull request. The full run on the development branch catches it after the merge.

## Beyond the minutes

The minutes are the part that I can count. I think that two other effects matter more, and I did not measure them:

- **Fewer checks on each pull request.** A check that runs on every pull request and tells the author nothing new is noise in the list of checks.
- **Less waiting.** A queue with fewer jobs starts the important ones sooner.

## Time, not minutes

Minutes are what GitHub bills. Time is what people wait for. In October I worked on time, on the same runners. In paired samples, release setup was almost 5x faster when the version is already published, and the read-only preparation of version metadata was about 6x faster. The core checks used 16.6% less runner time.

These are three separate paired cold samples on the same runner class. Each one has its own pair of commits and its own scope, so the percentages must not be added, and the first two must not be read as a faster test suite.

The first sample has the simplest cause. A release job installed the workspace and built every package before it asked whether there was anything to release. Now it asks first, with a small locked install of the Changesets CLI. When every version is already published, it does zero workspace installs and zero builds.

More from the same work:

- **The toolchain.** The compiler checks moved to tsgo, and Oxlint was upgraded. That sample measured compiler checks 22.2% faster and typed lint 17.7% faster.
- **A negative result.** Partial clones with full history were slower in the checkout sample, so the release jobs kept their fetch behavior.
- **Deleted tests are not a speed claim.** In the same change I deleted 43 mocked unit suites with 871 cases. That is a decision about test policy, and none of the numbers above include it.

Two older changes belong in the same list. In June, the test workflow got path-scoped gating, so a pull request skips the checks of packages that it does not change. In October, the host stopped building a web preview and an admin preview for each feature commit. A preview now builds when someone adds a label.

One practice from the November work is worth copying, and it has nothing to do with minutes. Every action is pinned by commit SHA, with the release named in a comment, and a release must be at least 7 days old before the repository uses it:

```yaml
steps:
  # The SHA is illustrative. Pin the commit of the release tag.
  - uses: actions/checkout@0123456789abcdef0123456789abcdef01234567 # v7.0.1
```

Two actions stayed on their older release for this reason: every newer release was less than 7 days old.

## What I did not measure

- **Usage after the change.** Every saving in this post is a projection from early November. I do not have the billing data for the weeks after, so there is no measured number.
- **The larger effects.** Fewer checks on a pull request and less waiting are the reasons I would give for this work. I measured neither.
- **The cost of a skipped test.** I know the case that the test selection can miss. I do not know how often it happens.
- **The basis of the projections.** Two rows rest on 20 hours of usage. That is a short window for a monthly number.
