This is the Dockerfile I start from for a Go service, followed by the reason for each line. I wrote [a worked example in 2024](/blog/2024-jun-golang-dockerfile-optimized/) that shrinks one image step by step and shows the sizes at each step. This post is the checklist that sits next to it.

The tags are Go 1.27.4, the current stable release, and the distroless images on Debian 13.

The numbers in this post come from one test service. It is a small HTTP server with four real dependencies (chi, pgx, the Prometheus client and zap): 18 modules and 310 packages. The machine is an Apple M4 with Docker Desktop 29.4.1, and all images are `linux/arm64`. Each time is the median of three runs.

## The complete Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

FROM --platform=$BUILDPLATFORM golang:1.27.4-trixie AS build
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src

COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /out/app /app
HEALTHCHECK --interval=30s --timeout=3s CMD ["/app", "healthcheck"]
ENTRYPOINT ["/app"]
```

It assumes the main package is in `./cmd/app` and that the binary has a `healthcheck` subcommand. Change both to match your project.

## Two stages: build in one, ship the other

The `build` stage has the Go toolchain. The final stage has one file from it, copied with `COPY --from=build`. The toolchain, the source and the intermediate files stay in the first stage and are not saved in the final image. Every other practice here depends on that split, because it lets the build image be large and convenient while the image you ship stays small.

## Pin the Go version and the base image

`golang:1.27.4-trixie` names a patch release and a Debian release. A tag like `golang:latest` or `golang:1` changes under you, and then a build that passed yesterday fails today with no change in your repository.

A tag can still be moved by its publisher. A digest cannot, so for a build that must not change, add the digest to the tag:

```sh
docker buildx imagetools inspect golang:1.27.4-trixie
```

```dockerfile
FROM golang:1.27.4-trixie@sha256:<digest from the command above> AS build
```

The cost is real: with a pinned digest you opt out of automated security fixes. So pin digests only if something (Dependabot can do it) opens a pull request when a new one appears.

### Keep the image version and go.mod in step

The official image sets `GOTOOLCHAIN=local`, so the `go` command in it never downloads another toolchain. The `go` line in `go.mod` is a minimum, and a module that a developer bumped to 1.27.4 on a laptop does not build on an image that is one release behind. On `golang:1.26.11-trixie` the build stopped at once:

```text
go: go.mod requires go >= 1.27.4 (running go 1.26.11; GOTOOLCHAIN=local)
```

That is the behaviour I want, because the error names both versions. With `GOTOOLCHAIN=auto` the same build passed after `go: downloading go1.27.4 (linux/arm64)`, but then the image tag no longer says which compiler built the binary, and each build without a warm module cache downloads a toolchain. Bump the `FROM` line in the same commit that bumps `go.mod`.

## Copy go.mod and go.sum before the source

Docker reuses a layer when the instruction and its inputs did not change. The source changes on every commit, but `go.mod` and `go.sum` change rarely. Copying those two files first means `go mod download` runs again only when the dependencies change, and an edit to a `.go` file starts the build at `COPY . .`.

<LayerCache />

On my test service the order alone saved little: a one-line edit to a `.go` file took 11.7 s with `COPY . .` first and 10.1 s with the module files first. The download was back in the cache, but the compiler still built all 310 packages. The next section removes that part.

### Private modules

A private module needs `GOPRIVATE`, so the `go` command skips the public proxy and checksum database for that path, and a credential for the host. The credential must not go in an `ARG`. After a build with `--build-arg GIT_TOKEN=not-a-real-token`, `docker history --no-trunc` printed it back:

```text
RUN |1 GIT_TOKEN=not-a-real-token /bin/sh -c echo using token >/dev/null # buildkit
ARG GIT_TOKEN=not-a-real-token
```

BuildKit warns about this (`SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data`), but the build still succeeds. A secret mount puts the file in place for one `RUN` instruction only:

```dockerfile
ENV GOPRIVATE=git.example.com/*
COPY go.mod go.sum ./
RUN --mount=type=secret,id=netrc,target=/root/.netrc \
    --mount=type=cache,target=/go/pkg/mod \
    go mod download
```

```sh
docker buildx build --secret id=netrc,src=$HOME/.netrc .
```

In my test the next instruction could not see the file, and the history showed only the command. For a token in an environment variable, `--mount=type=secret,id=token,env=GIT_TOKEN` exposes it to that one instruction, with `--secret id=token,env=GIT_TOKEN` on the command line.

## Cache mounts for modules and for the build cache

Layer caching is all or nothing: one changed dependency downloads all of them again, and one changed file compiles every package again. A cache mount fixes that. `RUN --mount=type=cache,target=...` gives the instruction a directory that persists across builds, so Go finds its module cache and its build cache from the last run.

The two targets are Go's two caches. `/go/pkg/mod` is the module cache, because the official image sets `GOPATH` to `/go`. `/root/.cache/go-build` is the build cache for the root user. The mounts live in the builder's local storage. They are not part of a layer, so the caches do not add to the image.

### Cache mounts on a fresh CI runner

Cache mounts are not included in an exported build cache: `--cache-to` writes layers, and a mount is not a layer. So a fresh CI runner starts with empty mounts unless the builder itself survives between jobs.

To measure it, each run built on a new `docker-container` builder with `--cache-to type=local,mode=max`, deleted the builder, edited one file, and built on a second new builder with `--cache-from`. That is a hosted runner with `type=gha` or `type=registry`, with a local directory as the store.

The `go mod download` layer came back as `CACHED`, and then the compile step ran with an empty build cache and took 10.6 to 16.1 s, as long as a cold build. The exported cache was 308 MB and saved nothing on the step that matters.

The mounts can be carried across by hand. A mount is keyed by its `target` unless you give it an `id`, so any Dockerfile that mounts `/root/.cache/go-build` on the same builder sees the same directory. One small Dockerfile archives both mounts into a local output after the build, and another unpacks them on the new builder before it. With the mounts restored, the compile step took 0.3 to 0.5 s. The archives were 79 MB of modules and 179 MB of build cache.

```dockerfile
# seed.Dockerfile, built with the restored archives as its context
FROM busybox:1.37
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=bind,source=.,target=/seed \
    tar -xf /seed/gomod.tar -C /go/pkg/mod && \
    tar -xf /seed/gobuild.tar -C /root/.cache/go-build
```

On GitHub Actions, `reproducible-containers/buildkit-cache-dance` packages the same two steps around `actions/cache`. For this service the trade is about 12 s per build against moving 258 MB. A self-hosted runner that keeps one long-lived builder needs none of this.

## CGO_ENABLED=0, and when you cannot use it

With cgo off, the binary does not link against a C library, and that is what lets it run on an image with no libc at all. The `net` package already prefers its pure Go resolver on Unix, so most services lose nothing.

You cannot turn cgo off if a dependency wraps C code. In that case, build with cgo on and change the final image to `gcr.io/distroless/base-debian13`, which adds glibc and libssl to what the static image has. Build on the Debian variant of the Go image, not on Alpine, so that the binary links against glibc and not musl.

## -trimpath and -ldflags="-s -w"

`-trimpath` removes file system paths from the executable. Stack traces then show module paths in place of `/src/...`.

`-s` omits the symbol table and debug information, and `-w` omits the DWARF symbol table. `-s` implies `-w`, so `-ldflags="-s"` gives a binary of the same size, to the byte. I keep both because that is the spelling people search for. Leave these flags out if you need the debug information in the production binary.

## Choose the final image

| | `scratch` | `distroless/static` | `alpine` |
| --- | --- | --- | --- |
| CA certificates | no | yes | yes |
| Timezone data | no | yes | no |
| Shell | no | no (`:debug` tag has busybox) | yes |
| Package manager | no | no | yes |

The binary is most of the image in the first three rows. Distroless static adds 3.4 MB to it, and for that you get the certificates, the timezone data and the user.

`scratch` is an empty image. A static Go binary runs on it, but the first outbound HTTPS request fails because there are no root certificates, and `time.LoadLocation` fails for a named zone because there is no timezone database. These are the two errors from my test service on `scratch`:

```text
Get "https://go.dev/": tls: failed to verify certificate: x509: certificate signed by unknown authority
unknown time zone Europe/Berlin
```
 You can fix both by hand: copy `/etc/ssl/certs/ca-certificates.crt` from the build stage, and build with `-tags timetzdata` to embed the timezone database. With Go 1.27.4 that added 393 KB to my binary.

The distroless static image has both already, plus a `/tmp` directory and an `/etc/passwd`, and it still has no shell and no package manager. That is why it is my default. When I need a shell in a running container, I rebuild with the `:debug-nonroot` tag and start it with `--entrypoint=sh`.

Alpine is the choice when the container must run other programs or you need to install packages at build time. Its base image has a shell, `apk` and a CA bundle but no timezone data. The same `LoadLocation` call failed on `alpine:3.24` and passed on both distroless images.

### When distroless is the wrong choice

Distroless static fits a pure Go binary that talks to the network and nothing else. It is the wrong base in three cases:

- **cgo.** A binary linked against glibc needs `distroless/base-debian13`, or `distroless/cc-debian13` when it also needs `libgcc`.
- **Other programs at run time.** A service that runs `ffmpeg`, `git` or a database client as a subprocess needs a distribution with a package manager. Use `debian:trixie-slim` and install only those packages, with `--no-install-recommends`.
- **A shell in production.** Distroless has nothing to `kubectl exec` into. `kubectl debug` with an ephemeral container replaces that habit, but the team has to adopt it first.

## Run as a non-root user

The `:nonroot` tag makes the container run as an unprivileged user with UID 65532, so the Dockerfile needs no `USER` line. On `scratch` there is no user database, but `USER` accepts numeric IDs:

```dockerfile
USER 65532:65532
```

On Alpine or Debian, create the user with an explicit UID and GID. Automatically assigned IDs can change between rebuilds.

In CI, scan the image you are about to push and fail on what you can act on:

```sh
trivy image --scanners vuln --ignore-unfixed --severity HIGH,CRITICAL --exit-code 1 registry.example.com/app:1.0.0
```

Run it on a schedule too, because a new CVE in a base image arrives without a commit in your repository.

## SBOM and provenance attestations

BuildKit can attach two records to the image: a software bill of materials and a provenance record of how it was built. Neither is signed by this step.

```sh
docker buildx build --sbom=true --provenance=mode=max -t registry.example.com/app:1.0.0 --push .
```

Both go into separate attestation manifests in the image index, so they do not change the image layers or the image digest that `docker run` pulls. On my test service the SBOM was a 664 KB SPDX document listing 27 packages: 20 Go entries (the modules, the standard library as `stdlib go1.27.4`, and the main module) and 6 Debian packages from the distroless base. The main module was listed with version `UNKNOWN`, because `.git` was not in the context. Provenance in `mode=max` was 14.7 KB and records the Dockerfile, the build arguments and the resolved base images, each with its digest. The default `mode=min` record was 1.3 KB.

The SBOM covers the final stage only, which is what ships. The Go entries come from the binary's build information, which `-s -w` does not remove: the stripped binary still gave the scanners every module and version.

## A .dockerignore file

`COPY . .` copies the whole build context, and any changed file in it invalidates that layer. A `.dockerignore` file in the context root keeps files out before they are sent to the builder.

```text
.git
.env
bin/
dist/
*.md
```

Two of those lines are about more than speed. `.env` stays out so that a secret never reaches a layer. Without `.git`, the `go` command has no repository to read, so the binary carries no version control stamp. Remove that line if you read the commit from `go version -m`.

### Version stamps and -buildvcs

When the context does include `.git`, the result depends on the build image. The Debian image has `git`, and the binary built in it carried the full stamp:

```text
mod    example.com/app  v0.0.0-20261121172147-28e4345f74c4
build  vcs=git
build  vcs.revision=28e4345f74c4439a8df11780f71e4e7d0e7ef751
build  vcs.time=2026-11-21T17:21:47Z
build  vcs.modified=false
```

The Alpine image `golang:1.27.4-alpine3.24` has no `git`. The same build passed there with no warning, and the main module version in the binary was `(devel)` with no `vcs` lines at all. A version endpoint that reads `debug.ReadBuildInfo` then reports nothing useful. The SBOM above shows the same gap.

`.git` can be larger than the source and changes with every fetch, so I keep it out and pass the commit in, with `-buildvcs=false` to make the intent clear:

```dockerfile
ARG VERSION=dev
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -buildvcs=false \
      -ldflags="-s -w -X main.version=${VERSION}" -o /out/app ./cmd/app
```

`docker buildx build --build-arg VERSION=$(git rev-parse --short HEAD) .` fills it in, and `main.version` must be a package-level `string` variable for `-X` to set it. A commit hash is not a secret, so an `ARG` is fine here. A changed `ARG` value is a cache miss from the first instruction that uses it, which here is the compile step.

## Multi-platform builds without emulation

`--platform=$BUILDPLATFORM` pins the build stage to the platform of the machine that runs the build. The compiler runs natively, and `GOOS` and `GOARCH` tell it what to produce. `TARGETOS` and `TARGETARCH` are set by BuildKit, but they are global, so each stage that reads them must declare them again with `ARG`.

```sh
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/app:1.0.0 --push .
```

On my arm64 machine, a build for both platforms took 13.4 s, and the amd64 compile step took 6.0 s of that. The build log shows it as `linux/arm64->amd64`: a cross-compile, with no emulator.

Without the pin, the build stage pulls the `golang` image for the target platform and runs the whole Go compiler under QEMU. I removed `--platform=$BUILDPLATFORM` and built `linux/amd64` on the arm64 machine with `--no-cache`, three times each way:

The pin works because the Go compiler cross-compiles on its own. With cgo on, the C compiler must also produce target code, so that build needs a cross C toolchain with `CC` set per platform, or emulation.

Multi-platform images also need an image store that supports manifest lists. Docker Desktop and Docker Engine 29.0 or later have one by default.

## HEALTHCHECK without a shell

The usual `HEALTHCHECK CMD curl ...` needs a shell and `curl`, and the final image has neither. The exec form, written as a JSON array, runs the binary directly. The `healthcheck` subcommand is code you write: it requests the service's own health endpoint and exits with 0 for healthy or 1 for unhealthy.

The defaults for `--interval` and `--timeout` are both 30 seconds. I set a short timeout because a health endpoint that takes three seconds is already a failure.

The first check runs one interval after the start. In my test the container reached `healthy` after 30.5 s, and one check took about 40 ms.

Kubernetes ignores this instruction and uses its own probes. There, the same subcommand works as an `exec` probe.

## Exec-form ENTRYPOINT and signals

`ENTRYPOINT ["/app"]` makes the binary PID 1. The shell form, `ENTRYPOINT /app`, starts `/bin/sh -c` as PID 1. Whether your binary then receives the `SIGTERM` from `docker stop` depends on the shell, so I timed `docker stop -t 10` on four images:

On Debian, the shell stays as PID 1 and does not pass the signal on. The binary never sees it, and Docker kills the container when the timeout ends. On Alpine, the shell replaces itself with a single command, so the plain shell form worked. It stopped working when the line had a second command. I would not depend on that difference: the exec form behaves the same on every image.

On distroless the shell form does not start at all, because there is no `/bin/sh`:

```text
exec: "/bin/sh": stat /bin/sh: no such file or directory
```

Receiving the signal is half of the work. By default a Go program exits on `SIGTERM` immediately, with requests still in flight. Use `signal.NotifyContext` with `SIGTERM` and call `Shutdown` on the HTTP server when the context is done.

## GOMAXPROCS and GOMEMLIMIT in a container

Since Go 1.25 the runtime reads the cgroup CPU limit and sets `GOMAXPROCS` from it. I ran a binary that prints the values on the 10-core machine. With no limit, `GOMAXPROCS` was 10. With `--cpus=2` it was 2, and with `--cpus=1.5` it was also 2, because the runtime rounds a fractional limit up.

Memory is different. With `--memory=256m` the soft memory limit stayed at its default, `math.MaxInt64`, so the garbage collector paces itself on heap growth alone. Set `GOMEMLIMIT` yourself, a little below the container limit:

```yaml
# Kubernetes container spec
resources:
  limits:
    memory: 512Mi
env:
  - name: GOMEMLIMIT
    value: 450MiB
```

## Common mistakes

- `FROM golang:latest`, or an unpinned final image such as `alpine:latest`.
- `COPY . .` before `go mod download`, which downloads every module again on each source change.
- Cache mount targets that do not match `go env GOMODCACHE` and `go env GOCACHE` inside the build image. The build still passes, only slowly.
- `CGO_ENABLED=1` with a `scratch` or `distroless/static` final image. The binary needs a libc that is not there, and the error does not say so: `exec /app: no such file or directory`.
- `scratch` without CA certificates, found only when the first HTTPS call fails in production.
- A `HEALTHCHECK` that calls `curl` or `wget` in an image without them.
- Shell-form `ENTRYPOINT` or `CMD`, which on most base images keeps `SIGTERM` away from the process.
- No `.dockerignore`, so `.git` and local `.env` files go into the build context.
- Reading `TARGETOS` or `TARGETARCH` in a `RUN` line without an `ARG` declaration in that stage. The values are empty.
- A token passed with `--build-arg`, which stays readable in `docker history`.
- A build image older than the `go` line in `go.mod`, which fails with `GOTOOLCHAIN=local`.
- Expecting `--cache-to` to carry cache mounts to the next CI runner.
