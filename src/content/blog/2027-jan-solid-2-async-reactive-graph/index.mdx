Solid 2.0 became stable on 16 November 2026. The biggest change is where async work lives. In 1.x, a fetch was a `createResource`. It was a separate primitive, with its own `loading` and `error` flags. In 2.0, any computation can return a promise. The reactive graph itself knows that a node is waiting.

This post explains that mechanism. It is for engineers who know promises, queues and transactions, but not signal graphs. I read the reactive core in the `solidjs/solid` repository, and I measured 2.0 against 1.9 with the same small app on an Apple M4.

## The graph in backend terms

Solid has three kinds of node:

- A **signal** holds a value. Think of it as a row.
- A **memo** is a cached result. It records the signals and memos that it read on its last run. It runs again only when one of them changes. Think of a materialized view that knows its own dependencies.
- An **effect** is a leaf. It does something outside the graph: it writes to the DOM, it logs, or it calls an API. Think of a subscriber on a change feed.

Use the figure below. Each button writes a signal. Look at the two counters: one write gives one memo run and one effect run. Two writes in the same tick also give only one run each.

<GraphPlayground />

Every memo and effect also has an **owner**. The owner is the computation that was running when the node was made. Owners make a tree. When a parent runs again or is disposed, Solid disposes its children first and runs their `onCleanup` callbacks. This is the rule of structured concurrency: when you cancel a task, you cancel its subtasks. There is one change in 2.0. A `createRoot` that you make inside another owner now belongs to that owner, and Solid disposes it with that owner.

```ts
import { createSignal, createMemo, createEffect, flush } from "solid-js";

const [price, setPrice] = createSignal(10);
const [qty, setQty] = createSignal(3);
const total = createMemo(() => price() * qty());

createEffect(
  () => total(), // compute: runs in the graph, records dependencies
  value => console.log("total", value) // apply: the side effect
);
```

In 2.0, an effect has two parts. The first function is tracked and returns a value. The second function gets that value and does the side effect. It can return a cleanup function. A 1.x effect with only one function fails in development, with a clear message. The last section shows the full text.

## Writes are queued, then flushed in height order

In 2.0, a write does not change what reads return. The write stages the value, marks the subscribers, and queues one microtask:

```ts
setPrice(12);
price(); // 10
flush();
price(); // 12
```

`schedule()` calls `queueMicrotask(flush)` one time per tick. All writes in the same synchronous run of your code go into that one flush. For this reason, `batch` is gone. Batching is the default. Use `flush()` in tests when you must see the new value at once.

The flush is a topological sort with a heap. Each memo has a height: one more than the highest memo that it reads. `runHeap` goes through the heap from height 0 upwards. Thus a memo always runs after all of its inputs, and each dirty node runs one time. Look at a diamond: two memos read one signal, and a third memo reads both of them. The bottom memo runs one time, with both new inputs. It never sees a pair where only one half is new. After the heap, the flush settles held changes. Then it runs render effects, and then user effects.

## What a pending node is

Now return a promise from a memo:

```ts
const [id, setId] = createSignal(1);
const user = createMemo(async () => {
  const userId = id(); // read inputs before the first await
  const res = await fetch(`/api/users/${userId}`);
  return res.json();
});
```

`handleAsync` sees a thenable. It stores the promise on the node as the current flight. The node gets a pending status, and a read of it throws a `NotReadyError`. The `source` of that error is the node. Solid also marks the dependents as pending, with the same source. It does not run them again, because there is no new input for them yet.

Each read of a pending node throws again. The reader does not block a thread, and it does not get `undefined`. It is like `EAGAIN`: the scheduler runs the reader again when its input arrives. In production builds on V8, the `NotReadyError` constructor sets `Error.stackTraceLimit` to 0. This throw happens on every read of a pending source. It is control flow, not a failure, so a stack trace is waste.

When the promise resolves, Solid first checks that this promise is still the current flight of the node. If `id` changed in the meantime, the node has a newer flight, and Solid drops the old answer. It is the same idea as a compare-and-set on a version number: a late response to an old request cannot overwrite a newer one. If the promise is current, Solid writes the value like any other write. It clears the pending marks from the dependents and schedules a flush. A rejection takes the same path with an error status. Solid wraps it in a `StatusError` and keeps the original error as `cause`.

<PendingNode />

There is one rule to remember. Solid records dependencies only up to the first `await`. It does not track a signal that you read after it. If that late read finds a pending source, the memo can never try again. So in development, Solid throws an error and does not hang: "Read of an unresolved async source after an `await`."

## Superseded flights are dropped, not cancelled

The check on landing protects the screen. It does not protect the server. Solid does not cancel requests itself. When a newer flight replaces an old one, the old flight still runs to the end, and Solid discards its answer. If you want the request to stop, the memo must do it. Every run of a computation is an owner. When Solid replaces a run that never reached the screen, it disposes that run and calls its `onCleanup` callbacks. Register an `AbortController` before the first `await`, and that disposal cancels the request:

```ts
const results = createMemo(async () => {
  const q = query(); // tracked: read before the await
  const ac = new AbortController();
  onCleanup(() => ac.abort()); // runs when a newer run replaces this one
  const res = await fetch(`/api/search?q=${q}`, { signal: ac.signal });
  return res.json();
});
```

I measured both versions with a typeahead. It loads one query, then gets four keystrokes 10 ms apart. Each keystroke calls a fake fetch that takes 50 ms.

- Without `onCleanup`, five fetches started and all five ran to the end. Solid discarded three of the answers when they landed.
- With `onCleanup`, five fetches started, three were aborted, and two finished: the first query and the last.

In both versions, the render effect ran two times, one time for each answer that it kept. The screen never showed the three discarded answers. The only difference is the work that the server did.

Solid does not clean up the run that is on the screen when a newer run starts. That run stays live until its replacement lands, because the user still sees it. Solid disposes only the runs between the two. With the attribution build on, Solid also reports the pattern. The `ABANDONED_FLIGHTS` diagnostic fires when one async source abandons three or more flights in one second. That is the sign of one request per keystroke.

## Boundaries catch pending and errors

Something must catch the throw. In 2.0, `<Loading>` catches pending reads. It was `Suspense` in 1.x. `<Errored>` catches errors. It was `ErrorBoundary`. The two are separate on purpose. A pending read is never an error, and `<Errored>` never shows its fallback for a wait.

<BoundaryCatch />

`<Loading>` catches pending reads only until it has shown content one time. After that, Solid **holds** a change that needs new async data. The screen keeps the old content. When every async value that the new frame needs has landed, the whole change appears in one frame. Think of a transaction. The writes go to a staged world. Readers of the visible world still see the committed snapshot. The commit is atomic. To get the fallback back for one specific change, use the `on` prop. It lists the dependencies that arm the boundary again: `<Loading on={id()}>`.

Two functions read the uncommitted state on purpose:

- `isPending(() => user())` is true while a new answer for that expression is in flight.
- `latest(id)` returns the newest written value while the hold is open.

I ran the memo above with a fake fetch of 50 ms and logged what an effect saw:

```text
[61ms] effect saw user = Ada
[61ms] isPending(user) = false  latest(id) = 1
[91ms] --- setId(2)
[92ms] isPending(user) = true  latest(id) = 2
[142ms] effect saw user = Grace
[142ms] isPending(user) = false  latest(id) = 2
```

The effect never saw an empty or half-loaded value. Between 92 ms and 142 ms it showed Ada. The two reads of the uncommitted state showed the change in flight correctly.

Errors follow the same graph. A `try`/`catch` around a reactive read in a memo does not catch an error from upstream. When a memo reads a source that has an error, the memo gets the error too. You recover through `<Errored>`. A rejected promise that your own code awaits is still a normal exception, and you can catch it.

If no `<Errored>` catches an error, Solid does not log it and continue. The error stops the scheduler. I rejected an async memo with no boundary above it. The development build printed this, then passed the error to `reportError`:

```text
[REACTIVITY_HALTED] An uncaught error halted the reactive system. No further updates will be processed. Handle errors with <Errored> or treat this as a crash.
  in computed
```

After that, Solid ignores all writes, also writes to signals that have no relation to the failed memo. In Node, the rejection also stopped the process. Put an `<Errored>` at the root, as you put a top-level exception handler in a server. Without it, one bad response stops all updates after it.

## Every change is a transition

1.x had `startTransition` and `useTransition`. 2.0 removes both, because every change is already a transition. The rules are short:

- A change is a write, the writes of an action, or an async answer that lands.
- All writes in one synchronous tick are one change.
- Solid holds a change when it would put a render effect on screen that reads async data with no answer yet. Until the answer comes, the screen keeps its frame.

Two details follow from these rules. First, only render effects hold. A memo that no render effect reads can stay pending forever and hold nothing. A memo that you create during a hold does not join the hold. It joins only when it reads a held value. Second, holds join through the graph, not through time. Two writes that share an async value on screen settle as one frame. Two writes that share nothing land separately, also when they are one millisecond apart.

Solid batches landings in the same way as writes. I made 1,000 async sources. Each one waits 20 to 29 ms on its own timer, and one effect adds them all.

- In 1.9, with `createResource` and `createEffect`, the effect ran 1,001 times on the first load: one time for the empty state, and one time for each resource. A change of the shared key made it run 1,000 more times.
- In 2.0, with async memos and a render effect, it ran one time on the first load and one time for each change.

The cost is the other side of the same rule. The effect shows nothing new until the slowest of the 1,000 sources has answered. For a list, that is usually correct. For two widgets on one page that have no relation, it is not. The next primitive is for that case.

## When waiting is wrong: createDeferred and quiet refreshes

`createDeferred` has the same name as in 1.x, but a new meaning. In 2.0 it is an async memo that can be late but is never early. Before its first answer, it is like any async memo. After that, a new fetch holds nothing. Its readers keep the last committed value until the new value lands, and the rest of the screen continues without it. `isPending` still shows the new fetch, so the widget can dim itself.

I connected a fast source (20 ms) and a slow source (200 ms) to one signal, and changed the signal one time.

- With both as `createMemo`, the two widgets kept the old value and changed together, 202 ms after the write.
- With the slow source as `createDeferred`, the fast widget changed at 23 ms and the slow one at 202 ms.

<DeferredTimeline />

`refresh()` is quiet by default. It asks the same question again, so the value on screen still answers it. `isPending` stays `false` for the full round trip. To show a reload as pending, declare it first: `affects(data); refresh(data)`. In the same test, `isPending(() => data())` was `false` 20 ms into a plain refresh. It was `true` 20 ms into a declared refresh, and it went back to `false` when the new value landed.

The other way to never suspend is `loadingValue`. It is a declared first paint. Its type is strictly `T`, so the placeholder must have the shape of a real answer. If the placeholder cannot have that shape, the source needs a `<Loading>` boundary.

## Optimistic actions and rollback

Mutations are not reads, so 2.0 has a separate primitive. `action()` wraps a generator. Each call runs as one transaction. Solid holds the writes in it until the body has returned and all work that it started has landed. At `yield`, the action waits for a promise and then enters its transaction again.

`createOptimistic` and `createOptimisticStore` give you values whose writes show at once. Solid discards these writes when the transaction ends. In the source, an optimistic write is a guess (`optimisticWrite`). At the next flush, each guess becomes the value of its node in a **lane**. A lane is a sub-transaction under the hold. The committed value under it does not change, so a rollback costs nothing: Solid drops the lane, and the committed value shows again. On success, the `refresh()` in the action fetches the source again, and the real value replaces the guess in the same frame.

```ts
let saved = 0;
const [count, setCount] = createOptimistic(() => saved);

const save = action(function* (n: number) {
  setCount(n); // shows now
  yield api.save(n); // the transaction stays open
  refresh(count); // read the source of truth again
});
```

With a fake `api.save` that rejected after 50 ms, the effect on `count` printed this:

```text
[1ms] effect saw count = 0
[3ms] effect saw count = 5
[53ms] effect saw count = 0
[53ms] action rejected: server said no
```

If you have written a saga, this is the compensating step, without the code for it.

## The same feature in 1.9 and 2.0

My test app is a list page. It loads 1,000 items through an async function, filters them by a text input, and toggles an item with an optimistic update. In 1.9:

```tsx
const [query, setQuery] = createSignal("");
const [items, { mutate, refetch }] = createResource(query, fetchItems);

const toggle = async (item: Item) => {
  const before = items();
  mutate(list => list?.map(i => (i.id === item.id ? { ...i, done: !i.done } : i)));
  try {
    await toggleItem(item.id);
  } catch {
    mutate(before);
  }
  refetch();
};
```

In 2.0:

```tsx
const [query, setQuery] = createSignal("");
const [items, setItems] = createOptimisticStore(() => fetchItems(query()), []);

const toggle = action(function* (id: number) {
  setItems(list => {
    const item = list.find(i => i.id === id);
    if (item) item.done = !item.done;
  });
  yield toggleItem(id);
  refresh(items);
});
```

The JSX changes too:

- `<Loading>` replaces `<Suspense>`, and `<Errored>` replaces `<ErrorBoundary>`.
- `class={{ done: item.done }}` replaces `classList`.
- `isPending(() => items.length)` replaces `items.loading`.
- `<For>` reads the store directly as `each={items}`.

The full component has 35 lines (not counting blank lines) in 1.9 and 33 in 2.0. The toggle handler goes from 11 lines to 8, and there is no manual snapshot and restore. The store setter takes a draft, so `produce` is gone too.

- With `renderToString`, with the rows already in memory.
- With `renderToStream`, where the rows come from an async loader under `<Loading>` (`<Suspense>` in 1.9). The stream goes into a Node `Writable` until it ends.

### Update time

The micro-benchmark is one signal with 10,000 dependents, in Node, with the browser builds of both versions. There are two shapes. In the first, the dependents are 10,000 effects. In the second, they are 10,000 memos, and one effect adds them. The time is from the write to the end of the flush. In 1.9, a write outside a batch runs its effects synchronously. In 2.0, I call `flush()`.

2.0 is slower on this shape. Every write in 2.0 is staged, then committed at the flush, also when nothing is async. The design notes of the reactive core do not allow a direct commit for each write. They call this commit cost the price of the semantics: reads must not change before the flush. One write that reaches 10,000 effects costs about one millisecond. Real pages rarely have that much fan-out from one signal.

## Running 1.x code on 2.0

I copied the 1.9 app into the 2.0 project with no changes and built it. The first failure is the import path:

```text
"./web" is not exported under the conditions ["solid", "module", "browser", "production", "import"] from package .../node_modules/solid-js
```

When I use `@solidjs/web` in place of `solid-js/web`, the compiler stops at the first removed JSX attribute:

```text
Error: `classList` on <li> was removed in Solid 2.0. Use `class` with an object or array instead: `class={{ active: isActive() }}` or `class={["base", { active: isActive() }]}`. (28:21)
```

After that, the bundler reports each removed export:

```text
[MISSING_EXPORT] "createResource" is not exported by "node_modules/solid-js/dist/solid.js".
[MISSING_EXPORT] "ErrorBoundary" is not exported by "node_modules/solid-js/dist/solid.js".
[MISSING_EXPORT] "Suspense" is not exported by "node_modules/solid-js/dist/solid.js".
```

`batch`, `startTransition`, `on`, `produce`, `createComputed` and `createMutable` are also gone from the 2.0 exports. `solid-js/store` is now `solid-js`. Code that compiles can still fail at run time in development. These messages come from the development build:

```text
[MISSING_EFFECT_FN] createEffect requires both a compute function and an effect function. Use `createEffect(() => signal(), value => doWork(value))`. If you want a derived value, use `createMemo`. If you want a one-shot side effect, just call the function directly.

[REACTIVE_WRITE_IN_OWNED_SCOPE] Writing to reactive state inside an owned scope (component, computation) is not allowed. Move the write outside or set the `ownedWrite` option if this is intentional. (in computed)

[STRICT_READ_UNTRACKED] Reactive value read directly in <Title> will not update. Move it into a tracking scope (JSX, a memo, or an effect's compute function).
```

- The first comes from a `createEffect` with only one function.
- The second comes from the 1.x habit of `createMemo(() => setDoubled(count() * 2))`.
- The third is a warning, not an error. It comes from a component that destructures its props.

Each message has a link to its page in the diagnostics reference.

Server functions are part of the change: in 2.0, the `"use server"` runtime is part of `@solidjs/web`.
