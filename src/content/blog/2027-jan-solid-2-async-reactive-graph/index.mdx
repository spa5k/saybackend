## The graph in backend terms

Since theres a graph, there will be nodes on it, and types of node, nice thing is that, its just 3 types of nodes you have to learn about or your agent have to consider

- Signal - It holds a value, it was quite a rage back then when it was released, with voices on both sides, but gradually everyone has surrendered to it, and it became part of 3 most popular libaries/frameworks other than react, to the point, there's even a TC39 Proposal to add it in the language itself.
- Memo - Memo holds cached result, similar to useMemo in react.
- Effect - By name, it does sounds like how useEffect in reactjs works, and it sort of does acts like useEffect, with some subtle changes, it has no dependency array, solidjs handles it automatically.

{/* There are three types of node:

- A **signal** holds a value. Think of a row. Everyone knows this one. SolidJS made it popular. [Svelte](https://svelte.dev/docs/svelte/runes) and [Angular](https://angular.dev/guide/signals) all have signals now. There is even talk of [adding them to JavaScript itself](https://github.com/tc39/proposal-signals).
- A **memo** is a cached result. It records the signals and memos it read on its last run. It runs again only when one of them changes. Think of a materialized view that knows its own dependencies. The memo is popular from [React.js](https://react.dev/reference/react/memo): you cache a value, and it does not render again. Typical thing.
- An **effect** is a leaf. It does work outside the graph. It writes to the DOM, it logs, or it calls an API. Think of a subscriber on a change feed. The effect was also borrowed from [React.js](https://react.dev/reference/react/useEffect). It is something that happens externally, and we need the result to reflect in the main graph. In Solid.js that graph is the reactive graph. In React.js it is the virtual DOM.

Use the figure below. Each button writes a signal. Watch the two counters. One write gives one memo run and one effect run. Two writes in the same tick also give one run each. */}

When a parent node is discarded and disposed off, Solidjs also cleans up its dependents and calls their onCleanup callback handler, the children and cleanedup up, this is how the structured concurrency works in solidjs, you cancel a task, you also cancel its subtasks.

## Writes are queued, then flushed in height order

In 2.0, a write does not change what the reads return, at least Not right away. The write stages the value, marks the subscribers, and queues one microtask:

```ts
setPrice(12);
price(); // 10
flush();
price(); // 12
```

schedule calls the queueMicrotask(flush) (it's an internal function), one time each tick. All the writes that has happened in one synchronous run of your code combine in that flush, thats why the old separate batching mechanism is gone, as batching is now the default mechanism. In tests, if you want to see immediate read, you do a `flush()`, but thats it.

Now when ti comes to flush, its a topological sort with a heap, each memo has a height, one more than the memo it reads from. Flush walks the heal from height 0 to upwards. The memo runs after all of its inputs. Each of the dirty node in the graph runs one more time.

And height is the depth of the node in the chain of the reads that happen. A signal has the height of 0. Check the diagram below, its realtively easy to understand.

{/* `schedule()` calls `queueMicrotask(flush)` one time per tick. All writes in one synchronous run of your code join that one flush as batch basically. This is why the separate `batch` is gone. Batching is the default now. Call `flush()` in tests when you must see the new value at once.

The flush is a topological sort with a heap. Each memo has a height: one more than the highest memo it reads. It walks the heap from height to to upwards, A memo always runs after all of its inputs. Each dirty node runs one time. Draw a diamond: two memos read one signal, and a third memo reads both. The bottom memo runs one time, with both inputs new. It never sees a half-updated pair. After the heap, the flush settles held changes. Then render effects run, then user effects.

Height is the depth of a node in the chain of reads. A signal has height 0. A memo has a height of one more than the tallest memo it reads. In the chain below, `net` sits at height 1, `tax` at height 2, and `total` at height 3. In the diamond, `list` and `sorted` share height 1, so the heap can run them in any order. The bottom memo runs one time, after both are fresh. */}

## What a pending node is

By name its obvious, a node that's pending, for example, in a case where it awaits a promise, that's a node that's marked as pending in the graph.

Here, we return a promise from a memo:

```ts
const [id, setId] = createSignal(1);
const user = createMemo(async () => {
  const userId = id(); // read inputs before the first await
  const res = await fetch(`/api/users/${userId}`);
  return res.json();
});
```

When you trigger this, the handleAsync (internal function), sees a thenable, not a value. So it stores the promise on the node as current flight (in progress), the not gets a pending status. If you try to read the pending node right now, it iwll throw a `NotReadyError`. The error itself comes from the node.
Solid marks the dependents of this node as pending too, so you cant read them as well. And it then does not run those dependents again unless the parent node resolves.

When the reading gives error, the reader does not blocks the read, it does not get undefined either, if you want to compare, it's more like `EAGAIN` instead. The scheduler runs the reader again when the input arrives. In the production builds of SolidJS on v8, the `NotReadyError` constructor sets the `Error.stackTraceLimit` to be 0. The throw happens on every read, it does not go and scan the slack. Very nice.

{/* `handleAsync` sees a thenable. It stores the promise on the node as the current flight. The node gets a pending status. A read of it throws a `NotReadyError`. The `source` of that error is the node. 
Solid marks the dependents as pending too, with the same source. It does not run them again. There is no new input for them yet.

Each read of a pending node throws again. The reader does not block a thread. It does not get `undefined` either. It is like `EAGAIN`: the scheduler runs the reader again when its input arrives. In production builds on V8, the `NotReadyError` constructor sets `Error.stackTraceLimit` to 0. The throw happens on every read of a pending source. It is control flow, not a failure. A stack trace there is pure waste. I like this detail a lot.

When the promise resolves, Solid first checks that this promise is still the current flight. Did `id` change in the meantime? Then the node has a newer flight, and Solid drops the old answer. Same idea as a compare-and-set on a version number. A late response to an old request cannot overwrite a newer one. 
If the promise is current, Solid writes the value like any other write. It clears the pending marks from the dependents and schedules a flush. 
A rejection takes the same path with an error status. Solid wraps it in a `StatusError` and keeps the original error as `cause`. */}

When the promise of the pending node finally resolves, solid first checks that the promise that resolves belongs to the current "render/flight", since what if the data itself has changed? it wants to make sure that old data does not show, since there's another promise from a newer flight in progress, think of it like versioning, only the latest version is considered.
And if the promise is current, solid writes the value like any other typical write, it then removes the pending marks from the node, and its dependents, and schedules a flush for the `microtask queu`
Rejection is also similarly treated, since error is a value as well, its just wrapped in `StatusError`, and keeps the original error in the `cause`.

## Superseded flights are dropped, not cancelled

As I explained about the latest flight, what do you think happens with the requests that are triggered one after the other for same thing, with no one returning yet? They get cancelled.
But cancelling isn't enough since the cancelling by default is just ignoring their data by solid, to truly stop them and make sure they don't reach backend or backend stops them, you need to add `AbortController` to them.

(Explain how each request taking 50ms, and 4 requests happen, only first and last shows, rest 2 discarded, create a diagram as well showing this, with and without abort controller`)


{/* 
The check on landing protects the screen. It does not protect the server. Solid does not cancel requests itself. When a newer flight replaces an old one, the old flight still runs to the end. Solid discards its answer. Want the request to stop? The memo must do it.

If more than one flight of a request happens together, the superseded flights still run in the backend, even when you are not handling them correctly. Their result will not appear on the frontend. For example, if you are doing four flights together, only the first one and the last one can appear.

Every run of a computation is an owner. When Solid replaces a run that never reached the screen, it disposes that run and calls its `onCleanup` callbacks. Register an `AbortController` before the first `await`. That disposal cancels the request: */}

```ts
const results = createMemo(async () => {
  const q = query(); // tracked: read before the await
  const ac = new AbortController();
  onCleanup(() => ac.abort()); // runs when a newer run replaces this one
  const res = await fetch(`/api/search?q=${q}`, { signal: ac.signal });
  return res.json();
});
```

{/* I measured both versions with a typeahead. It loads one query, then gets four keystrokes 10 ms apart. Each keystroke calls a fake fetch that takes 50 ms.

- Without `onCleanup`, five fetches started and all five ran to the end. Solid discarded three of the answers when they landed.
- With `onCleanup`, five fetches started, three were aborted, and two finished: the first query and the last.

In both versions, the render effect ran two times, one time for each answer it kept. The screen never showed the three discarded answers. The only difference is the work the server did.

To manage this correctly, you should use an abort controller, similar to how `context` works in Golang. Everything should use an abort controller. You should probably create a helper function, so that it is managed automatically.

Solid keeps one exception. It does not clean up the run that is on the screen when a newer run starts. That run stays live until its replacement lands, because the user still sees it. Solid disposes only the runs between the two. With the attribution build on, Solid also reports the pattern. The `ABANDONED_FLIGHTS` diagnostic fires when one async source abandons three or more flights in one second. That is the one-request-per-keystroke smell. */}
Its better to create a helper function for your async calls so that abort controller is there by default. There's one exception that SOlid still keeps, it does not clean up the dat that's still on screen even when a newer run has started, as the user is still seeing it, it's only updated when the replaccement lands.

## Every change is a transition

1.x had `startTransition` and `useTransition`. 2.0 removes both. Every change is already a transition. The rules are relatively short:

- A change is a write, the writes of an action, or an async answer that lands.
- All writes in one synchronous tick are one change.
- Solid holds a change when it would put a render effect on screen that reads async data with no answer yet. Until the answer comes, the screen keeps its frame.

I think this is a big change, but a very nice one. When everything is a transition, it is relatively easier for the agent, and even for your mental model, to remain consistent. You don't need to understand lots of things. As long as everything is a transition, and you understand how it works, it does not really matter.

Two details follow. First, only render effects hold. A memo that no render effect reads can stay pending forever and hold nothing. A memo made during a hold does not join it. It joins when it reads a held value. Second, holds join through the graph, not through time. Two writes that share an async value on screen settle as one frame. Two writes that share nothing land separately, also when they are one millisecond apart.

Solid batches landings in the same way as writes. I made 1,000 async sources. Each one waits 20 to 29 ms on its own timer, and one effect adds them all.

- In 1.9, with `createResource` and `createEffect`, the effect ran 1,001 times on the first load: one time for the empty state, and one time for each resource. A change of the shared key made it run 1,000 more times.
- In 2.0, with async memos and a render effect, it ran one time on the first load and one time for each change.

That pair of numbers is the drawing on the share card of this post, by the way.

The cost is the other side of the same rule. The effect shows nothing new until the slowest of the 1,000 sources has answered. For a list, that is usually correct. For two widgets on one page that have no relation, it is not. The next primitive is for that case.

## Optimistic actions and rollback

Mutations are not reads, so solid v2 has a separate primitive for them, the `action()` wraps a generator, each call runs as one transaction. Solid holds the writes in it until the body has returned and all work it started has landed, and when it `yield`s, the action waits for a promise and then enters its transaction again.

`createOptimistic` and `createOptimisticStore` give you values whose writes show at once. 
```ts
let saved = 0;
const [count, setCount] = createOptimistic(() => saved);

const save = action(function* (n: number) {
  setCount(n); // shows now
  yield api.save(n); // the transaction stays open
  refresh(count); // read the source of truth again
});
```

With a fake `api.save` that rejected after 50 ms, the effect on `count` printed this:

```text
[1ms] effect saw count = 0
[3ms] effect saw count = 5
[53ms] effect saw count = 0
[53ms] action rejected: server said no
```

If you have written a saga, you will find this shape familiar. It is the compensating step, minus the code you wrote for it.

```text
[MISSING_EFFECT_FN] createEffect requires both a compute function and an effect function. Use `createEffect(() => signal(), value => doWork(value))`. If you want a derived value, use `createMemo`. If you want a one-shot side effect, just call the function directly.

[REACTIVE_WRITE_IN_OWNED_SCOPE] Writing to reactive state inside an owned scope (component, computation) is not allowed. Move the write outside or set the `ownedWrite` option if this is intentional. (in computed)

[STRICT_READ_UNTRACKED] Reactive value read directly in <Title> will not update. Move it into a tracking scope (JSX, a memo, or an effect's compute function).
```

- The first comes from a `createEffect` with only one function.
- The second comes from the 1.x habit of `createMemo(() => setDoubled(count() * 2))`.
- The third is a warning, not an error. It comes from a component that destructures its props.

Each message links to its page in the diagnostics reference. I wish every framework did this. :crown:

To move a full SolidStart app, with the router and the server, read [migrating a SolidStart app to Solid 2.0](/blog/migrate-solidstart-to-solid-2/). Server functions are part of the change: in 2.0, the `"use server"` runtime is part of `@solidjs/web`. For projects that use SolidStart today, read [SolidStart is in maintenance: what to use now](/blog/solidstart-maintenance-what-to-use/) first.
