An agent that says "done" has proved nothing. In our monorepo at work, agents write most pull requests, and for six weeks they also had a skill that let them verify a change in the running app. Then I counted what the recorded runs contained.

Of 160 recorded runs, 30 had a user-level check. That is 18.75%. The other 130 did not.

This post is about the two halves of the fix. The first half gives an agent the tools to prove a change in the real app, on its own machine, in parallel with other agents. The second half makes it impossible for the evidence to say more than the agent proved. The second half matters more, and it gets the most space.

## What went wrong with the first version

The first version of the skill gave agents five steps: launch, health check, drive, evidence, and cleanup. A feature map held a recipe for each product area, so that an agent did not have to rediscover how to start a workflow run or open a chat.

In use, four things went wrong. Agents repeated expensive setup. CLI flags were silently ignored. Useful failure details were lost. Agents wrote tests and guidance that nobody needed. The fixes were plain:

- Options are defined one time for all 20 drivers.
- Unknown, repeated, and missing options are rejected before any action. An agent that invents a flag gets an error, not a run that ignores it.
- The destructive steps have dry runs.
- The default for tests is no new tests. Each new integration test needs approval of the exact cases before the agent writes it.

Two more changes followed. Verification moved to coherent checkpoints in the work, and proof that still applies is used again. Each preview environment gets one synthetic account, so there is no account pool to lease from.

The feature map also moved away from the product. One example shows how small the cause can be. A loading guard in a script waited for the text `Loading step details...`, with three dots. The interface renders the single character `…`. The guard never matched.

## Why one agent at a time

The agents also worked under hard limits. The full development stack used one shared lease and two fixed ports, and about 48 worktrees shared them. One agent at a time could use the app.

Two more limits made it worse. Each preview environment needed a database branch, and we often reached the limit on branches at the host. And the shared local database stopped for every worktree when one worktree was deleted.

An agent that cannot reach the app can verify only what it can reach.

**A feature map and a planner.** The map lists 65 feature areas. Each one has its source paths, its entry points, its test suites, and the lowest tier that can verify it. A check fails when a product file has no owner in the map, so the map cannot drift in silence again. The planner reads the diff and prints the features that it touches, the tier, the checks, and the commands in order.

The planner picks the lowest tier that can run the claim. Before this change, the `local` tier meant the one shared stack.

**One web instance for each checkout.** A command builds this checkout's web app and starts it on its own port and hostname. Many checkouts run at the same time. One instance uses about 9x less memory than the full development stack.

A start takes about 20 seconds after a build.

**One database for each pull request.** The start command always creates a separate database project for the checkout, applies all its migrations there, and points the web instance at it. It starts only the services that the app uses: the database, the gateway, PostgREST, and Realtime. That is 4 containers (about 500 MB), and it takes about 52 seconds from zero to a usable instance. Two pull requests never share a database.

A pull request with a migration is the hard case, and it ran one time on a separate database: 282 migrations applied in 63 seconds. The shared database stayed where it was.

**Test data and flags.** A seed command fills the test account with realistic data, and cleanup removes all of it. A feature flag can be switched on for one instance through a local stand-in for the flag service. No product code changes for that, so the override cannot exist in production.

**Teardown.** One command removes the account and the seed rows, stops the web instance, destroys the database project with its containers and volumes, and removes the images that the run built. Then it lists what remains. A leftover gives exit code 1.

## Evidence that cannot say more than was proved

The tools above make a real check possible. They do not make an agent run one. An agent with a working app can still record a command that printed something, call it a pass, and move on. So the recorder has rules, and the agent cannot talk its way past them.

Each check is a record with fixed fields. This one is written for the post, with the field names of the real format:

```json
{
  "name": "The saved filter survives a reload",
  "required": true,
  "level": "user",
  "status": "passed",
  "action": "Set the filter on the list page, then reload",
  "expected": "The list shows the same filter",
  "observed": "The filter is set after the reload",
  "oracle": "Row read from the database after the reload",
  "evidence": ["filter-after-reload.png"]
}
```

The field that does the work is `oracle`. It says how a separate result confirmed the action. A page that showed the right text is an observation. A stored row that was read after a reload is an oracle. A check that passes needs at least one evidence file, and a check that does not pass needs a reason.

`level` has three values: `setup` for a prerequisite, `local` for a local handler, and `user` for the product path. The report shows the highest level that the run observed. It does not turn a local check into a user-level one, and that is the number at the top of this post.

Three of these rules each close one shortcut.

**No assertion.** A command against the web instance that returns a response has shown that the server answers. It has not shown that the answer is right. With no assertion, the record is `incomplete`.

**A pattern that matches everything.** The next move is an assertion that cannot fail: an empty pattern, or one that matches any text. The recorder refuses both.

**The quiet retry.** A check fails. The agent runs a different command that passes, and records that one. The recorder keeps the failed attempt, and the new one can replace it only with a stated reason. Earlier attempts stay in the report.

Two more rules keep the headline true. The result of a check and the result of the run are separate, so a run with passing assertions can still end as `blocked`. An intentional test proved this: both browser assertions passed, and the verifier still exited as blocked, because a required identity check at the end was missing. And the report headline covers all checks, not the best ones.

Fourteen evidence cases test these rules, and each verdict is as designed.

## The trial: ten pull requests

I gave the tools to ten agents and ten real pull requests, in two waves, with up to four agents at the same time.

- **7 passed.**
- **2 could not check the main claim**, because the pull request had a migration. The tools now start one database for each pull request, so a migration no longer needs the shared one.
- **1 found a real schema defect**, which is now fixed.

There was no collision on a port, an account, or a database. The first wave took about 10 minutes for each pull request. The second wave used three different models, and the tool defects from the first wave did not appear again.

I also replayed the planner on 200 commits of the main branch, to check that later cleanup had changed no plan and lowered no tier.

Two of the ten runs ended with "could not check the main claim". That is the result the rules are for: the run states the gap, and the report does not hide it behind a smaller claim that passed.

## One incident

During this work, an early version of the teardown, run by an agent, stopped the shared database one time by mistake. The rule that decides whether a resource is "in use" was wrong. It is corrected, and checks now cover it.

## What I did not measure

- **A pull request with a migration, after the last change.** It ran on the earlier version. It did not run again after the change to one database for each pull request.
- **Two live instances with two databases at the same time.** The project names and the port ranges are different by construction. I did not run the two together.
- **A journey with a paid model.** No check in the trial called a paid model.
- **The last round of fixes.** It had no independent review and no third wave.
- **The rate after the change.** 30 of 160 is the number before these tools. I do not have the same count for the weeks after.
