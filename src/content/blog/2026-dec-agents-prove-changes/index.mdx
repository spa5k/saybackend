In our monorepo at work, coding agents write most pull requests. An agent that says "done" has proved nothing. In October 2026 we gave the proof to the agents: a verification skill that lets an agent start the real app, use the change the way a user would, and attach the evidence.

We did not get it right in one step. We started from a generated base and improved it for seven weeks, each time from what real use showed. Where it stands now:

- **Every change ends the same way**: review, verification, and one report on the pull request, from every agent.
- **Each agent has its own copy of the app.** It uses about 9x less memory than the shared stack, and its own database is ready in about 52 seconds.
- **Ten agents verified ten real pull requests**, up to four at the same time, with no collision on a port, an account, or a database.
- **The daily development stack went from 14.1 GB to 2.4 GB of memory.**
- **A report cannot say more than the agent proved.**

## Start from a base skill

The first version stands on [pstack](https://github.com/cursor/plugins/tree/main/pstack), a public pack of agent skills. Its `/create-verification-skill` reads a repository and generates a verification skill for it. The shape it gives is the useful part:

- **Launch.** The exact command that starts the app, and how to tell that it is ready.
- **Health check.** One read-only check that answers "is this instance worth driving?"
- **Drive.** How to use the app the way a user does, with the real selectors and commands of this repository.
- **Evidence.** What to capture for a proof, and where it goes.
- **Cleanup.** How to remove what the run started, and keep the evidence.

It also seeds a feature map: one recipe for each product area, so that an agent does not have to rediscover how to start a workflow run or open a chat.

Our first version, on 3 October, had 62 files: 31 scripts, their tests, and recipes for three product areas. Its first proof was one workflow that passed on the local stack and again through the normal interface on the hosted path.

## Make it the default

A skill that an agent may use is used on some days. Five days later the guide of the repository made it the rule: every task that changes code or runtime configuration ends with review, then verification. One sentence of that rule does most of the work: "Start both yourself; do not ask first or wait for a prompt."

The order is fixed. The agent reviews its own diff with [a code review skill](/blog/pr-review-agents-what-stuck/), fixes the confirmed blockers, and then verifies. The report goes to the pull request as one comment, and a later run updates that comment in place.

This is the consistent half of the title. A reviewer no longer has to guess what an agent ran. Every pull request carries the same kind of report, with what passed, what failed, what was blocked, and what was not tested.

## Three weeks of use

By late October, real use had shown four habits. Agents repeated expensive setup. They passed CLI flags that the scripts silently ignored. Useful failure details were lost on the way up. And agents wrote tests and guidance that nobody needed.

The fixes were plain:

- **Options are defined one time for all 20 drivers.** An unknown, repeated, or missing option is rejected before any action. An agent that invents a flag gets an error, and not a run that ignores the flag.
- **Destructive steps have dry runs.**
- **The error of a child command reaches the top**, with its exit code.
- **The default for tests is no new tests.** Each new integration test needs approval of the exact cases before the agent writes it.

## Make a run cheap enough to repeat

A check that is expensive gets skipped, by people and by agents. Four changes made a run cheaper:

- **Verify at checkpoints.** Related edits are verified together at a coherent point in the work. A fix repeats only the checks that it affects, and proof that still applies is used again.
- **One command.** Teammates use a command of the repository and do not need the skill pack installed.
- **One synthetic account for each preview environment.** There is no pool of accounts to lease from.
- **Previews on request.** A preview environment is built when someone adds a label, and no longer for each commit.

## A maintenance pass

A feature map starts to go stale on the day the app changes. pstack has a second skill for this, `/maintain-verification-skill`: it reads every feature recipe against the source, drives every feature live, and ships at most one pull request of proven corrections. It may edit only the skill.

Our first pass, in early November, changed 21 files. One correction shows how small the cause of a broken check can be. A loading guard in a script waited for the text `Loading step details...`, with three dots. The interface renders the single character `…`. The guard had never matched.

Of 160 runs, 30 had a check at the level of a user. The same data showed why such a check was hard to get. The full development stack had one shared lease and two fixed ports, and about 48 worktrees shared them. One agent at a time could use the app. An agent that cannot reach the app verifies what it can reach without it.

Two more limits pushed the same way. Each preview environment needed a database branch at the host, and we often reached the limit on branches. And the shared local database stopped for every worktree when one worktree was deleted.

**One web instance for each checkout.** A command builds this checkout's web app and starts it on its own port and hostname, so many checkouts run at the same time. One instance uses about 9x less memory than the full development stack, and it starts about 20 seconds after a build.

**One database for each pull request.** The start command creates a separate database project for the checkout, applies all its migrations there, and points the web instance at it. It starts only the services that the app uses, which is 4 containers (about 500 MB), and it takes about 52 seconds from zero to a usable instance. Two pull requests never share a database.

**Test data and flags.** A seed command fills the test account with realistic data, and cleanup removes all of it. A feature flag can be switched on for one instance through a local stand-in for the flag service. No product code changes for that, so the override cannot exist in production.

**Teardown.** One command removes the account and the seed rows, stops the web instance, destroys the database project with its containers and volumes, and removes the images that the run built. Then it lists what remains, and a leftover gives exit code 1.

## Evidence that cannot say more than was proved

The tools make a real check possible. They do not make an agent run one. An agent with a working app can still record a command that printed something, call it a pass, and move on. So the recorder has rules.

Each check is a record with fixed fields. This one is written for the post, with the field names of the real format:

```json
{
  "name": "The saved filter survives a reload",
  "required": true,
  "level": "user",
  "status": "passed",
  "action": "Set the filter on the list page, then reload",
  "expected": "The list shows the same filter",
  "observed": "The filter is set after the reload",
  "oracle": "Row read from the database after the reload",
  "evidence": ["filter-after-reload.png"]
}
```

The field that does the work is `oracle`. It says how a separate result confirmed the action. A page that showed the right text is an observation. A stored row that was read after a reload is an oracle. `level` has three values: `setup` for a prerequisite, `local` for a local handler, and `user` for the product path. The report shows the highest level that the run observed, and it does not turn a local check into a user-level one.

Three of these rules each close one shortcut.

**No assertion.** A command against the web instance that returns a response has shown that the server answers. It has not shown that the answer is right. With no assertion, the record is `incomplete`.

**A pattern that matches everything.** The next move is an assertion that cannot fail: an empty pattern, or one that matches any text. The recorder refuses both.

**The quiet retry.** A check fails. The agent runs a different command that passes, and records that one. The recorder keeps the failed attempt, and the new one can replace it only with a stated reason.

Fourteen evidence cases test these rules, and each verdict is as designed.

## The trial: ten pull requests

I gave the tools to ten agents and ten real pull requests, in two waves, with up to four agents at the same time.

- **7 passed.**
- **2 could not check the main claim**, because the pull request had a migration. The tools now start one database for each pull request, so a migration no longer needs the shared one.
- **1 found a real schema defect**, which is now fixed.

There was no collision on a port, an account, or a database. The first wave took about 10 minutes for each pull request. The second wave used three different models, and the tool defects from the first wave did not appear again.

Two of the ten runs ended with "could not check the main claim". The evidence rules exist for that result: the run states the gap, and the report does not hide it behind a smaller claim that passed.

The last audit was of the stack that every engineer and every agent starts each day. On one machine, idle and signed in, it used 14.1 GB.

Most of it was the web app in development mode: 12.1 GB in 24 processes. The server process held 7 GB, and a second development server, 17 loader workers, and the bundler of one package held most of the rest. Memory settings for the bundler and the workers did not move the number. A production build did. The web app now runs as a production build by default, in 2 processes and 1.2 GB, which is about 10x less.

The trade is hot reload. An edit is served after a rebuild of 18 to 22 seconds. The old server answers during the build, and the switch takes about 1 second. A flag brings hot reload back for work on the interface.

The containers got the same treatment. The local database stack ran 10 containers, and the app uses 5 of them. The ClickHouse container got a memory limit, after it had grown to 1.59 GB in one day without one. The whole stack is ready in about 62 seconds.

A stack of 2.4 GB leaves room on the same machine for the agents and their own instances.

## What I did not measure

- **The share of user-level checks after the change.** 30 of 160 is the count before the parallel tools. I do not have the same count for the weeks after.
- **Time from the start of a change to its merge.** "Faster" in this post rests on what I did measure: agents that work at the same time and no longer one at a time, the start times, and the memory. I have no before and after for the whole path.
- **A pull request with a migration, after the last change.** It ran one time on an earlier version: 282 migrations applied in 63 seconds on a separate database. It did not run again after the change to one database for each pull request.
- **Two live instances with two databases at the same time.** The project names and the port ranges are different by construction. I did not run the two together.
- **A journey with a paid model.** No check in the trial called a paid model.
- **The last round of fixes.** It had no independent review and no third wave.
- **Other machines.** The numbers of the daily stack are from one machine.
